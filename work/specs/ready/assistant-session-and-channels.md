## Problem Statement

The user wants ONE general-assistant agent they can talk to from anywhere (Telegram first, later WhatsApp, and wherever itself as a chat app via push notifications), that can act PROACTIVELY (scheduled jobs, reminders, "tell me when X"), and that remembers what matters across resets without depending on one ever-growing transcript.

Existing options do not fit:

- **OpenClaw** does this but brings far more than wanted (its own runtime, integrations and conventions), and does not tie into wherever.
- **`badlogic/pi-telegram`** (MIT, a single `index.ts` pi extension) is a Telegram DM bridge INTO one running pi session: it polls only while that session is up and `/telegram-connect`ed, so a reset or restart needs a manual reconnect. It has no scheduler and no way for the agent to start a conversation (purely reactive), and its Telegram-specific inbound, outbound and session ownership are fused together, so it cannot grow a second channel. It is a remote control for a session, not an assistant. Its Telegram mechanics (long polling, draft streaming with `sendMessageDraft` falling back to `sendMessage` + `editMessageText`, 4096-char splitting, inbound file download, `stop`) are good and reusable.

wherever already owns most of the hard parts:

- an always-on server holding pi sessions (`server/src/session-pool.ts`), whose `sendUserMessage` already reaches BOTH server-built sessions and CLI-bridge sessions (relayed as `cli_message`, handled in `extension/src/index.ts`);
- self-contained custom tools registered in both session types (`attach_file`, `say`, with a drift test);
- an opt-in special folder precedent: `searchFolder` in the config, with `maybeSeedSearchWorkspace` dropping a default `AGENTS.md` once;
- web composer `/new` and `/reset`, handled locally in `ChatInput.svelte`, which already create a new session in the current folder;
- a PWA service worker (`web/src/service-worker/index.ts`) that ALREADY handles `push` events (declarative `web_push: 8030` payloads, foreground postMessage vs `showNotification`) and `notificationclick` with a `navigate` target.

What is missing: the assistant folder + session pointer, a channel seam, a scheduler, a way for a CLI-bridge tool to CALL the server, the push subscription + send side, and the web surfaces to reach it all.

## Solution

All inside wherever, opt-in:

1. **The assistant folder + assistant session (opt-in, like `searchFolder`).** A config key `assistantFolder` with NO default: unset = feature off (no tools in server-built sessions, no channels, no scheduler, nothing written; CLI-bridge sessions always carry the tool twins, which then return a "not configured" error, see decision 11). The folder is the assistant's HOME and MEMORY, seeded once with a default `AGENTS.md` (and `jobs/AGENTS.md`, `.gitignore`). The SESSION is disposable; the FOLDER is the memory. Exactly one session in that folder is the CURRENT assistant session (a pointer the server keeps in its state dir). "Reset" = a fresh session in the folder becomes the pointer target.
2. **A channel seam in the server.** One interface every transport implements. v1 adapters: **Telegram** (porting pi-telegram's mechanics) and **Web Push** (wherever as the chat app). WhatsApp later. The web UI is the session as it is today, plus an Assistant entry point.
3. **A server-owned scheduler.** Jobs are written by the `assistant_schedule_*` tools (callable from ANY session) into the assistant folder's `schedule.json` and always RUN as the assistant: **inline** (delivered into the current assistant session once it is settled with nothing queued) or **isolated** (a fresh session in `<assistantFolder>/jobs/`, started immediately, in parallel). NOT the system crontab, whose detached `pi -p` output has nowhere to go.
4. **`assistant_notify` + message-level routing.** A REPLY goes back to the channel of the user message it answers (the web always shows the session). ANYTHING NOT A REPLY reaches the user ONLY through `assistant_notify`, which is delivered IMMEDIATELY (never waits for a running turn) and is visibly distinct from a reply on Telegram. No automatic push on turn end.
5. **A bridge request/response path** so the `assistant_*` tools also work in a CLI-bridge session: the wherever pi extension (which already holds a WebSocket to the server) gains a request message with a correlation id, and the server answers it.

## User Stories

1. As a user, I want the assistant to be OPT-IN with no default folder (I set `assistantFolder` myself, like the search folder), so that nothing changes for an install that does not want it and no `assistant_*` tool appears in server-built sessions unless I enabled it (terminal pi sessions always carry the tools, which then answer "assistant not configured").
2. As a user, I want a single general-assistant conversation I can reach from Telegram, so that I can ask it things from my phone's messaging app without opening wherever.
3. As a user, I want the same assistant reachable from the wherever web app through an Assistant entry point that always opens the CURRENT assistant session, with a push notification when it deliberately tells me something while I am away, so that wherever works as a chat app for it.
4. As a user, I want to reset the assistant's session whenever I like (`/new` or `/reset` on Telegram, `/new` or `/reset` or a Reset button in the web) without losing what it has learned, so that context stays small and fresh.
5. As a user, I want the assistant to keep its durable memory, INCLUDING its schedule, as plain files in its folder, so that I can read, edit, version (git) and back up what it remembers and what it will do.
6. As a user, I want the assistant to schedule its own jobs ("every morning at 8, brief me on X", "remind me Friday about Y", "check Z every hour and tell me if it changes"), so that it can be proactive.
7. As a user who travels, I want "every morning at 8" to mean 8 where I am NOW, while "call mom at 6pm her time" stays pinned to her timezone, so that reminders arrive at the right local time.
8. As a user, I want to see, edit and cancel scheduled jobs (by asking any agent, or by editing the file), so that nothing runs that I do not know about.
9. As a user, I want a heavy, slow or possibly-urgent job to run off to the side (isolated, in parallel) and only notify me with its result, and the assistant to DELEGATE long work that way instead of blocking our conversation, so that the conversation stays responsive and readable.
10. As a user, I want to hear from the assistant ONLY when it deliberately notifies me (or answers something I sent), so that proactivity never turns into noise.
11. As a user, I want a notification to reach me IMMEDIATELY even while the assistant is busy in a Telegram exchange with me, and to be visibly marked as a notification (not part of the current conversation), so that important things are never delayed and never confused with replies.
12. As a user working in ANY wherever session (e.g. a coding session), I want that session's agent to be able to hand a scheduled job to the assistant ("check CI in 30 minutes and tell me"), so that I get follow-ups without switching sessions, and that job lands in the assistant's single schedule where I can see it.
13. As a user working in ANY wherever session, I want that session's agent to be able to notify me through the assistant's channels ("the deploy finished", "tests are red"), and tapping the notification to open THAT session, so that I am made aware of things wherever I am.
14. As a user, I want only ME to be able to talk to the assistant on Telegram, paired with a one-time code shown in the web UI (or a configured user id), with a re-pair action in the web, so that whoever finds the bot handle first cannot claim it.
15. As a user, I want a Telegram message sent while the assistant is mid-turn to STEER that turn (as the web composer does), and Telegram to SHOW me it steered rather than started a new turn, so that I understand what happened to my message.
16. As a user, I want `!command` shell shortcuts refused on channels and in scheduled prompts, so that nothing the assistant controller feeds in can run a shell command or raise a sudo prompt without an agent turn.
17. As a user, I want files to flow both ways on a channel (send an image or document in; the agent's `attach_file` delivers out), so that the assistant is as useful as in the web app.
18. As a user, I want to stop a running turn from any channel (`stop`), so that the channel behaves like the web composer.
19. As a user, I want the assistant to keep working (channels connected, schedules firing) across wherever restarts and session idle eviction, so that proactivity does not depend on a tab or terminal staying open.
20. As a user, I want to be able to attach a terminal pi to the assistant session (CLI bridge) and still have channels AND the `assistant_*` tools work, so that I can drive it from a terminal when I want to.
21. As a user, I want isolated job sessions to live in their own `jobs/` subfolder, so that they group separately in the sidebar and never put the main assistant session into the "folder in use" read-only state.
22. As a maintainer, I want transports behind one channel interface, so that adding WhatsApp (or email, Signal, ...) is an adapter, not a redesign.
23. As a maintainer, I want server-written assistant state in the STATE dir and secrets resolved and scrubbed per ADR 0007, so that a read-only (sops-nix) config dir keeps working (ADR 0006) and the agent's shell cannot read the bot token.

## Resolved decisions

1. **Opt-in via `assistantFolder` in the config, NO default**, mirroring `searchFolder`. Unset = no tools registered in server-built sessions, no channels started, no scheduler, no state written (CLI-bridge sessions keep their always-registered twins, which return "not configured", per decision 11). Seeded once if absent, never overwritten: `AGENTS.md`, `jobs/AGENTS.md`, `.gitignore` (excluding `.assistant.lock`). A change to `assistantFolder` takes effect on server restart.
2. **Schedule intent lives IN THE ASSISTANT FOLDER; run state lives in the STATE dir.** `<assistantFolder>/schedule.json` holds only what the user/agent DECIDED and is hand-editable and versionable. Entry: `{id, name, cron? | at?, tz?, mode: "inline"|"isolated", prompt, enabled, originSessionId?, originCwd?}`. Exactly one of `cron` (5-field cron expression, recurring) or `at` (ISO 8601 date-time, or `"now"`, one-shot) is present. The server NEVER writes run bookkeeping into it, so it cannot clobber a hand edit. Run history is an append-only `assistant-runs.jsonl` in the state dir (one line per firing: job id, time, mode, session file, outcome); last/next run are derived from it plus the schedule. All tool writes to `schedule.json` go through ONE in-process queue on the server (CLI-bridge calls arrive at the server through decision 11, so there is one writer), write atomically (tmp + rename), and re-read and retry if the file changed on disk since it was read. The server validates on every read; a malformed entry is logged and shown as invalid in `assistant_schedule_list`, never starts a turn, and does not stop valid entries firing. A completed one-shot stays in the file and is listed as done (from the run log) until removed.
3. **Timezones: jobs follow the USER by default, or are pinned.** A job without `tz` is evaluated in the user's CURRENT timezone; a job with `tz` (IANA name) is pinned to it ("call mom at 6pm her time"). The user's current timezone is server STATE (it changes when travelling), initialised to the system timezone, and updated (a) automatically by the web client, which reports `Intl.DateTimeFormat().resolvedOptions().timeZone` on connect, and (b) by the `assistant_set_timezone` tool when the user tells the assistant. The assistant always knows it: every turn of a session in `assistantFolder` (or `jobs/`) gets a one-line system-prompt append `User's current timezone: <tz>` at `before_agent_start` (the conversation-mode inline-extension pattern for server sessions; for CLI-bridge sessions the extension fetches `assistant_info` (returns `assistantFolder` and the current timezone, or "not configured") ONCE at register time, caches the answer including negative ones ("unsupported" on timeout from an old server, "not configured"), and is pushed an update by the server when the timezone changes; `before_agent_start` reads the cache and never waits on the network). Telegram cannot report a timezone. An `at` value without a UTC offset is read in the job's effective timezone.
4. **Restart rules.** A recurring job that missed one or more runs while the server was down fires ONCE on startup if the most recent missed run is within a grace window (default 1 h, configurable), otherwise it is skipped and the skip recorded. A one-shot whose time passed while down follows the same grace rule, then counts as done.
5. **One server per assistant folder; a second is a loud misconfiguration.** `assistantFolder` is set deliberately, so two servers on one folder is a user error, not a case to support. The lock is `<assistantFolder>/.assistant.lock` (pid, host, boot id, process start time). A server that finds a live lock refuses to start the assistant (channels, scheduler, tools report it) and logs why. A lock from the SAME host is stale, and taken over, when the boot id differs or the pid is dead or now belongs to a process with a different start time (pid reuse after a reboot). A lock from ANOTHER host is never taken over automatically: the log says to remove it by hand. Boot id and process start time come from `/proc` on Linux; on darwin use `sysctl kern.boottime` and `ps -o lstart=`, and degrade to a pid-only check where neither is available.
6. **No handoff turn on reset, and no automatic reset.** `AGENTS.md` tells the agent to save what matters continuously; memonaut recall (when installed) covers the rest; pi's auto-compaction bounds context size.
7. **Reset = a new non-job session in the assistant folder becomes the pointer target.** Triggered by Telegram `/new` or `/reset` (handled by the controller, never sent to pi), the web Reset button, or the web composer's existing local `/new` / `/reset` while in the assistant session (any NEW session created in `assistantFolder` itself, not in `jobs/`, from the web or a CLI terminal becomes the current one). All creation paths pass `forceNew=true` (`createNewSession` otherwise returns the folder's viewed session). Reset during a running turn ABORTS it; pending queued messages of the old session are dropped and reported on the channels they came from.
8. **Mid-turn channel messages STEER** (matching the web composer and ADR 0003); Telegram shows it with a reaction on the user's message (falling back to a short "added to the current reply" note).
9. **Inline jobs wait until the assistant session is SETTLED with no queued messages** (pi's `agent_settled`, not `agent_end`, which can fire between chained internal runs), then are delivered as a normal message `[schedule:<name>] (from <originCwd>, session <originSessionId>) <prompt>`; a prompt that starts with `/` (e.g. `/skill:...`) is sent WITHOUT that prefix so command and skill expansion still work (decision 15), its job context living in the run log only. After an ABORTED settle of the assistant session (`agent_settled` with `aborted: true`), pi still holds any queued messages (abort does not clear them), so the controller calls `clearQueue` and reports the dropped messages on the channels they came from (as for a reset), and "settled with no queued messages" is reachable again. They never queue behind or merge into a running exchange. Anything urgent belongs in an ISOLATED job, which starts immediately in parallel.
10. **Reply routing is per USER MESSAGE, not per run, and the POOL owns it** (web sends never pass through the controller, so only the pool sees every send; the controller just passes an origin along with its sends). The pool records an origin for every send that WILL PRODUCE a user message (`telegram`, `schedule:<jobId>`, ...; web-typed messages record `none`), keyed by session file (so a CLI takeover of a server session keeps them), in one queue per delivery mode (prompt-or-steer, and followUp), because pi keeps steer and followUp in separate queues and delivers steers first. A send produces no message, and so records nothing or has its entry dropped, when: it is a `!`/`!!` shell send; the session is not resident (a silent no-op today); `prompt()` reports `preflightResult` `"handled"` (an extension command or input handler consumed it); or the send throws (e.g. during compaction). To observe `preflightResult`, the pool sends EVERY message (plain text and steers too, not only `/`-prefixed text) through `prompt(text, {expandPromptTemplates: false, streamingBehavior, source: 'extension', preflightResult})`, which is equivalent to today's plain-text `sendUserMessage` path; a `prompt()` that returns without calling `preflightResult` was DEFERRED (called during an `agent_settled` emit) and is treated as pending, not handled. `cancelSteerQueue` / `clearQueue` clears both routing queues. At `agent_settled`, each routing queue is TRIMMED to pi's current queue length, keeping the newest entries (server sessions: `getSteeringMessages()` / `getFollowUpMessages()`; pi's queues are NOT necessarily empty, since abort leaves them in place); for CLI sessions, whose pi queues the server cannot see, the routing queues are emptied. The pool does this BEFORE it fans `agent_settled` out to the controller, so an inline job the controller sends from its settled handler keeps its entry. So the queue can never drift permanently. Bounded CLI caveat: the server cannot see `preflightResult` in a CLI session, so a `/command` an extension handles there while idle leaves a stale entry that can take the next channel message's slot until the next settle. The trigger is a user `message_end` event (pi emits `message_start` and `message_end` back to back for each user message; the CLI extension already forwards `message_end` but not `message_start`, so `message_end` works for both session types): it takes the head of the matching queue, and that origin becomes the current destination for assistant output until the next user message. Matching is by queue position, never by text (`/skill:` and prompt-template expansion change the text). A user message typed directly in a CLI terminal has no queued send of its own: it gets no channel origin when the matching queue is empty; if the queue is not empty, position matching gives it the head entry, a misattribution corrected at the next settle. So a Telegram steer into a scheduled turn sends everything after the steer to Telegram, a scheduled message's output goes to no channel, and web or terminal messages are visible only in the session.
11. **`assistant_*` tools in CLI-bridge sessions: always registered there, errors at call time.** Part of the single BRIDGE FOUNDATION task (its full contents are listed once, in the seed's "Bridge foundation" bullet): the wherever pi extension's existing WebSocket gains `cli_request {id, op, args}` (extension to server) and `cli_response {id, ok, result | error}` (server to extension), with a timeout. The extension ALWAYS registers the CLI twins (a stable tool set keeps the prompt cache warm); a call returns a clear error when the bridge is disconnected or disabled, when the server says the assistant is not configured, or on timeout (which is how an OLD server is detected: `handleWSMessage` has no default case and `cli_register` has no ack, so an unknown `cli_request` is silently dropped). The server resolves the calling session from the bridge registration and stamps origin itself. This is a foundation task; the extension is a separately published package (`@wherever-dev/pi`) and ships with its own changeset.
12. **Server-built sessions register the `assistant_*` tools only when `assistantFolder` is configured** (decided in `buildServerAgent()`). Tools: `assistant_schedule_add`, `assistant_schedule_list` (marks jobs that came from the caller, shows done and invalid entries), `assistant_schedule_remove`, `assistant_set_timezone`, `assistant_notify`.
13. **Notifications come ONLY from `assistant_notify`, are delivered IMMEDIATELY, and are visibly distinct.** Arguments: `{title, body, navigateSessionId?, jobId?}`. It never waits for a running turn. Where a tap lands: `navigateSessionId` if given; else, if `jobId` is given or the caller is an isolated job session (the controller maps it to its job), the job's origin session; else the calling session. On Telegram a notification is sent as its own message prefixed `🔔 <source>: <title>` (source = origin folder or session name), never folded into a reply, so it cannot be confused with the current exchange. A scheduled turn that does not call it is silent apart from being visible in the session.
14. **Telegram pairing is by one-time code** (shown in the web UI while Telegram is enabled and unpaired; the user sends `/pair <code>` to the bot) or by a configured user id, which takes precedence over a stored pairing. `/start` and `/pair` are refused once paired; re-pairing is an explicit web action. Messages from any other user are ignored.
15. **`!command` and `!!command` are refused for everything the controller feeds in** (channel messages AND scheduled prompts, inline or isolated), with a short explanation; the text never reaches the pool's shell path. Slash commands and `/skill:` expansion keep working: the origin is tracked by the pool's routing queue (decision 10), never as a text prefix in front of a `/`.
16. **Telegram token handling (ADR 0007 shape).** Resolution: `WHEREVER_TELEGRAM_TOKEN`, then `WHEREVER_TELEGRAM_TOKEN_FILE`, then a config-file value; never argv. After reading, the env variables are SCRUBBED from `process.env` (the agent's `bash` inherits the server environment, so a prompt-injected agent could otherwise exfiltrate the token). An unreadable token file disables Telegram with a loud error rather than failing the whole server: ADR 0007's fatal rule exists because a missing AUTH token fails open, which does not apply to an optional channel.
17. **Push recipients = every registered subscription.** Single-user server, one shared token: subscribe/unsubscribe for the current device in settings, 404/410 prunes.
18. **wherever sends Web Push itself; it does NOT depend on `push-notification-server`.** That service is multi-tenant, keyed on `(address, domain)` with signer-based registration, and has an unauthenticated `/push` (its own `docs/findings/trigger-service-integration.md`). For a single-user self-hosted server, VAPID + the Web Push protocol in-process is a small module with no extra deployment. Its WebCrypto sender (`packages/server/src/web-push/`) may be borrowed if it is cleaner than the `web-push` npm package. The unused template subscribe client in `web/src/lib/core/service-worker/push-notifications/` (no importers) is DELETED and replaced by a small client against wherever's own token-gated endpoint.
19. **Isolated jobs run in `<assistantFolder>/jobs/`.** They group separately in the existing folder-grouped sidebar and never share a folder with the main assistant session (which would trigger the folder-conflict read-only state). pi loads `AGENTS.md` from the working directory and its parent directories (pi-coding-agent `docs/configuration.md`), so jobs inherit the assistant's instructions; `jobs/AGENTS.md` adds the job-specific ones. Retention is a later concern.
20. **WhatsApp is deferred.** The seam must allow it.

## Implementation Decisions (seed)

> Seed for tasking; trimmed once tasked.

- **Where things live (ADR 0006 / 0007).**
  - CONFIG dir (read-only to the server, written by the operator): `assistantFolder`, enabled channels, Telegram allowed user id (optional), grace window, Telegram token as a last-resort value, the VAPID `subject` contact (a `mailto:` or URL required by Web Push; default derived from the configured public URL).
  - STATE dir (written by the server, `getWhereverStateDir()`, next to `drafts.json`): the current-session pointer, the user's current timezone, Telegram pairing result + polling offset, the VAPID keypair (generated on first use, mode 0600), push subscriptions, `assistant-runs.jsonl`.
  - ASSISTANT folder (shared with the user and the agent): `AGENTS.md`, `jobs/AGENTS.md`, `.gitignore`, memory files, `schedule.json`, `.assistant.lock`.
- **Assistant controller (server).** Owns the folder lock, the pointer, reset (abort, then `createNewSession(folder, ..., forceNew=true)`), the mapping from the pool's per-message destination (decision 10, owned by the pool) to channel delivery, the settled-wait queue for inline jobs, the job-to-session map for isolated runs, the `!` refusal, and the user timezone. Calls `loadSession` on the pointer before every send (the pool's `sendUserMessage` is a silent no-op on a non-resident session; needed for story 19). Pins the current assistant session against the CLI idle-teardown race (an idle CLI session with no viewers is destroyed and reconnects with backoff; a channel message in that window would build a server agent on the same file). Moves the pointer when a new session is created in `assistantFolder` itself (not `jobs/`) from the web OR a CLI terminal: the pool gains a session-created callback (today it has only the single `onEvent` slot), fired from `createNewSession` only on a REAL creation (not when it returns an existing viewed session) and from `cli_register` only for a NEW CLI session. `cli_register` is re-sent on every reconnect and pi's `session_start` reason is `"startup"` for both a fresh `pi` and `pi -c`, so the bridge foundation task adds an `isNew` flag and a `capabilities` list to `cli_register`. `isNew` = the session context had no messages at `session_start` (`buildSessionContext().messages.length === 0`, the check pi's own SDK uses; NOT an entry count, since pi writes `model_change` / `thinking_level_change` entries into every new session), and it is sent as true only on the FIRST `cli_register` after that `session_start`, so a reconnect (even of a still-empty session) never moves the pointer. With an older extension that sends no `isNew`, a session created from a CLI terminal does not move the pointer (expected, not a bug). The controller then aborts the old pointer session's running turn exactly as for any reset. The pointer move is idempotent (the controller's own reset and job creation also go through `createNewSession` and fire the callback), so a reset aborts once. "Idle" for inline jobs means SETTLED with no queued messages, not `agent_end` (which can fire between chained internal runs such as retry or compaction); CLI sessions do not forward `agent_settled` today (the bridge foundation task adds it); for an older extension without that capability, the controller falls back to `agent_end`.
- **Channel interface.** `start()`/`stop()`; inbound `onUserMessage({channel, text, files, senderId})` to the controller; outbound `deliverReply(...)` fed from the session's event stream for output whose current destination is the channel (streaming where supported); `notify({title, body, source, navigate, files?})`, always immediate. `pool.onEvent` is a single slot today (`server/src/index.ts`), so it gains a fan-out (or the controller subscribes alongside the WS broadcaster).
- **Images and files in.** The pool's `sendUserMessage` takes text only; inbound Telegram files are saved into upload staging and passed as paths like web uploads. Passing images as model image inputs (as pi-telegram does) needs an images parameter on the pool send; that is its own small task.
- **Telegram adapter.** Port pi-telegram's long polling, draft/edit streaming, 4096 splitting, file in/out, `stop`. Steer feedback via `setMessageReaction`. `/new`, `/reset`, `/pair`, `/start`, `stop` handled by the adapter/controller. Notifications as separate `🔔`-prefixed messages with a link to the target session when the wherever public URL is configured.
- **Web surfaces.**
  - An endpoint exposing assistant status (configured, current session id, lock state, channel states, pairing state, current timezone), exposed to the web like `searchFolder` is today.
  - An "Assistant" entry point (sidebar/home) that opens the CURRENT assistant session, and a Reset action on it.
  - Telegram pairing UI in settings: the one-time code while unpaired, the paired user, a re-pair action.
  - Push toggle in settings calling `PushManager.subscribe` with the server's VAPID public key; token-gated `POST`/`DELETE` subscription endpoint.
  - The web client reports its timezone on connect (decision 3).
  - Fix the FOREGROUND notification click: it uses SvelteKit `pushState` (`web/src/lib/core/notifications/index.ts`), which does not fire the `hashchange` `+page.svelte` listens to, so a `/#<sessionId>` target does not open the session.
  - No change needed for the web composer's local `/new` / `/reset`: it already creates with `forceNew` (`ChatInput.svelte` to `session_new`, whose server handler calls `createNewSession(..., true)`); the session-created callback above is what turns it into an assistant reset.
- **Web Push send.** `{web_push: 8030, notification: {title, body, navigate: '/#<sessionId>'}}` to every subscription, matching the SW's `DeclarativePushNotification` shape.
- **Scheduler.** Single timer loop over validated `schedule.json` entries (re-read on change via a watcher or each tick), next run derived from `cron`/`at`, the effective timezone (job `tz` or the user's current one) and `assistant-runs.jsonl`. Inline = queued in the controller until the assistant session is settled with nothing queued, then sent. Isolated = controller creates a session in `jobs/` immediately (`forceNew`), records the job mapping, sends the prompt.
- **Bridge foundation (one task, one `@wherever-dev/pi` changeset; the ONLY place its contents are listed).**
  - `cli_register` gains `isNew` (rule in the controller bullet) and `capabilities` (at least `agent_settled`, `cli_request`).
  - The extension forwards `agent_settled`.
  - `cli_request` / `cli_response` on the existing CLI WebSocket: correlation id, timeout, typed `op` (`schedule_add`, `schedule_list`, `schedule_remove`, `set_timezone`, `notify`, `assistant_info`). The server handler resolves the calling session from the bridge's registration.
  - A server-to-extension `assistant_info_changed {assistantFolder, timezone}` push (sent on a timezone change), updating the extension's cached `assistant_info`.
  - The extension fetches `assistant_info` once after register and caches it, negative answers included.
- **CLI-side timezone append (`@wherever-dev/pi`, own changeset):** the extension's `before_agent_start` appends `User's current timezone: <tz>` from the cached `assistant_info` when the session's cwd is `assistantFolder` or its `jobs/`; never waits on the network. Blocked on the bridge foundation.
- **Tools.** Server: `customTool`s in `buildServerAgent()` calling the controller directly (only when configured). Extension: `pi.registerTool` twins, always registered, calling `cli_request`. Shared descriptions held in sync by a drift test like `say-tool.test.ts`.
- **Default `AGENTS.md`.** Long-lived general assistant; session may be reset any time, so save anything worth keeping into files here as you go (`memory/`, `profile.md`, ...) and read them at the start of a fresh session; use `assistant_schedule_*` for anything time-based (no `tz` = follows the user; set `tz` only for things pinned to a place); DELEGATE long-running or slow work to an isolated job (`at: "now"`) that notifies when done, instead of blocking the conversation, and make anything possibly urgent isolated; the user hears from you only through replies and `assistant_notify`, so in a `[schedule:...]` turn call `assistant_notify` if the user should hear about it; when the user says where they are, call `assistant_set_timezone`; if a `recall_search` tool is available, prefer it over asking the user to repeat themselves.
- **Default `jobs/AGENTS.md`.** You are an isolated job run by the assistant: do the task, save anything worth keeping under `../memory/`, call `assistant_notify` if the user should know the result, and do not start conversations.

## Testing Decisions (seed)

> Seed for tasking; trimmed once tasked.

- **Isolation (WORK-CONTRACT shared-write rule).** Every test points `assistantFolder` at a temp dir and sets `WHEREVER_CONFIG_DIR` / `WHEREVER_STATE_DIR` to temp dirs (resolved in-process), and asserts the real home folders and `~/.wherever` are untouched. Telegram Bot API and the push service are mocked at the HTTP boundary.
- **Opt-in:** with `assistantFolder` unset, no `assistant_*` tool is registered in server sessions, no channel starts, nothing is written anywhere.
- **Scheduler:** next-run derivation for `cron` and `at` (including `"now"`) from the run log; follows-the-user vs pinned `tz`, including a user timezone change and a DST transition; missed-run grace rule across a simulated restart (fire once inside the window, skip outside, one-shot done); inline waits for idle and never merges into a running exchange; isolated starts immediately in `jobs/` even while the assistant is busy; a malformed entry is listed as invalid without starting a turn while valid ones fire; a concurrent on-disk edit is not clobbered by a tool write. Injected clock, no real timers.
- **Lock:** a live lock makes a second server refuse the assistant with a clear report; a same-host lock with a dead pid, a reused pid (different start time) or a different boot id is taken over; a foreign-host lock is not.
- **Controller:** reset uses `forceNew` and yields a new session even with a web viewer on the old one; a web- or CLI-created session in `assistantFolder` (not `jobs/`) moves the pointer; a web message sent between a Telegram message and its reply does not take Telegram's routing slot; routing works identically for a CLI-bridge session (driven by `message_end`); in a SERVER session, a web `!cmd` or an extension-handled `/command` followed by a Telegram message still routes the reply to Telegram (no queue drift); at `agent_settled` routing queues are trimmed to pi's queue length (server) or emptied (CLI); a `stop` while a Telegram steer is queued drops and reports that message, after which an inline job fires and the next Telegram message routes correctly; an inline `/`-prefixed scheduled prompt is sent without the `[schedule:...]` prefix and still expands; inline jobs wait for settled, not `agent_end`, falling back to `agent_end` for an extension without the capability; a CLI reconnect (`isNew` false) never moves the pointer; a controller-initiated reset aborts exactly once; reset mid-turn aborts and reports dropped queued messages; routing is per user message (a Telegram steer into a scheduled turn sends only post-steer output to Telegram; scheduled output reaches no channel); `!`/`!!` refused for channel AND scheduled prompts.
- **Notify:** delivered immediately while a Telegram exchange is mid-turn; Telegram copy is a separate `🔔`-prefixed message; `navigate` precedence (explicit id, job origin, caller) holds; errors clearly when not configured.
- **Channels:** Telegram ignores unpaired senders, pairs only with the right code, configured id wins over stored pairing, refuses `/start` once paired, shows a steer marker on a mid-turn message, splits under 4096, `stop` aborts; `/skill:` messages still expand; the token env variables are absent from `process.env` after startup; an unreadable token file disables Telegram without failing the server. Web Push registration is token-gated, payload matches the SW's `web_push: 8030` shape, 404/410 prunes; the foreground notification click opens the target session.
- **Bridge:** `cli_request` round-trips with origin stamped server-side; timeout (old server), disconnected/disabled bridge and not-configured each give a clear tool error; `assistant_info` is fetched once at register, negative answers are cached, a server timezone push updates the cache, and `before_agent_start` never waits on the network.
- **Tools:** drift test between server and extension twins; server sessions have the tools only when configured; CLI sessions always have them.

## Out of Scope

- WhatsApp, Signal, email adapters (the seam must allow them).
- Jobs that RUN in another session's folder or inside the originating session. Any session can schedule, but every job runs as the assistant; the origin is context, not the execution location.
- Automatic reset and automatic push on turn end.
- Per-device push management, group chats, multi-user assistants.
- A restricted tool policy for channel-originated turns beyond the `!` refusal.
- A retention policy for isolated job sessions.
- Depending on or extending `push-notification-server`.
- Voice notes over Telegram (could later reuse the cloud STT path behind `/session/transcribe`).
