# Decisions taken while building `restore-create-folder-action` (2026-09-09)

In-scope choices the task did not specify, recorded here (per CLAIM-PROTOCOL) so a reviewer can ratify or reverse them rather than reverse-engineer them. None met the ADR gate on its own (each is cheap to reverse and sits under `docs/adr/0009`), but each is visible to a user or to the next reader of the panel.

1. **Create is a DISCLOSURE, not a button beside Clone.** The task says to keep the action "visually secondary" and to stop it becoming the accidental default tap; the shape chosen is a `<button>` reading "This folder was never a clone? Create it instead" which reveals the checkbox and a secondary-styled Create button, all under a separator. Rationale beyond weight: an accidental Create is not a no-op that the user can simply retry past. It produces an EMPTY folder, the session then loads as normally restored, and the registry's non-empty guard REFUSES the clone that should have happened, so the mistake has to be undone in a terminal, which is the one thing this feature exists to avoid. Alternatives considered: two buttons side by side (rejected, a thumb on a phone), and a radio/segmented "Clone | Create" mode switch (rejected, it puts the rare remedy at equal rank and re-titles the whole panel). Reversible: it is one branch in `RestorePanel.svelte`.

2. **The panel calls `fetchConfig()` itself when it opens for a folder.** `gitInitDefaultStore` is otherwise populated only by `SessionBrowser`'s connect effect, which is skipped in the read-only view and could have run long before, so the checkbox would have shown a stale or default-`false` value that is not the server's configured one. The call rides in the existing per-folder pre-fill effect (so it is once per folder, never per keystroke or per render), sits behind the same token gate as the `/remote-candidates` call beside it, and is a plain config read that shells out to nothing. Alternative considered: carrying `gitInitDefault` on the `folder_missing` frame (rejected: the frame is on the session-load path and `restore-remote-candidates` already set the precedent of keeping non-essential resolution off it).

3. **The checkbox travels EXPLICITLY as `gitInit` in both states**, never omitted when off. `restore_start` makes `gitInit` optional and the registry treats absent as false, so omitting it would happen to work today, but it would mean the answer is re-decided away from the screen the user ticked. Sending the observed value keeps the panel the single place the default is resolved, which is what "the checkbox honours configuration" has to mean.

4. **The user's tick wins over a later config change, per panel opening.** `gitInitChoice` is null until the user touches the checkbox and the configured default owns the value while it is; once touched, the tick holds even if `/config` answers afterwards. This mirrors `userManualGitInit` in the new-session dialog (`ChatMessageList.svelte`) deliberately, so the two git-init checkboxes behave the same. The choice resets when the panel opens for a DIFFERENT folder.

5. **The in-flight guard for Create is panel-local (`createRequested`), not a new client-state field.** The clone side derives "my tap is out, no answer yet" from `RestoreInfo.requestedUrl`, which a create has none of. Adding a `requestedAction` to the shared client's `RestoreInfo` would have been symmetric but changes a published type for a purely visual guard. Alternative considered and left open: if a second consumer ever needs to know which remedy this client asked for, promote it to `RestoreInfo` then.

6. **The panel is kind-aware for wording only** (`job.kind === 'create'`): "Creating the folder" instead of "Cloning <url>", "the folder creation was cancelled", no submodule note, and no scope label on the progress line (a create has exactly one scope, so naming it is noise rather than honesty). The states themselves are untouched: one state machine, one set of frames, one ready-and-reload ending, as the task requires.

7. **Tests.** The WebSocket-seam suite is a NEW file (`server/test/restore-create-folder-action.test.ts`) rather than more cases in `restore-clone-panel.test.ts`, because it needs no git fixtures, no slow-clone template and no network shape at all: creating a folder talks to nothing. Its targets are two levels below anything that exists and the seed removes the whole subtree, so "and any missing parents" is actually exercised. Registry-level create coverage already exists in `restore-jobs.test.ts`; this suite asserts only what the protocol seam adds (the frames, the filesystem result per checkbox state, the shared refusals, and the reload that yields a live session).
