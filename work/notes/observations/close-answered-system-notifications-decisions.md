# close-answered-system-notifications: decisions (2026-11-25)

In-scope choices made while building task `close-answered-system-notifications` (spec `notifications-compact`, story 21, resolved decision 1). Each is cheap to reverse; the code is `web/src/lib/core/notifications/answered-notifications.ts` (pure selection `answeredNotifications`, closer `createAnsweredNotificationCloser`, browser wrapper `browserNotifications`), wired in `web/src/lib/core/notifications/index.ts` (`answeredNotificationCloser`) and `web/src/lib/wherever.ts`.

1. **Fed from the frame handler, not the store.** `wherever.ts` passes each `shipmates_update` frame to the closer as it is received (`applyShipmatesUpdate` now returns the parsed state). Subscribing to `shipmatesStore` would also deliver the cached and initial values, which the task forbids. Alternative: a store subscription with a "skip first value" flag (fragile across reconnects). Touches: `applyShipmatesUpdate`'s return type only.
2. **"A few seconds" is 5 s** (`CLOSE_GRACE_MS`), the same order as the question toasts' 5 s wait and enough to absorb a small server/device clock skew when `data.sentAt` (server clock) stands in for `Notification.timestamp` (device clock).
3. **The snapshot's time is when this page received it** (device clock): the server's frame has no timestamp, and adding one would touch the protocol for no gain within the grace.
4. **Coalescing: sweep on the latest frame after 1 s of quiet** (`SWEEP_SETTLE_MS`). Frames queued while a page was frozen are delivered in a burst on return (the code base notes that timers fire before them, ADR 0011); acting on the first, older frame of a burst could close a notification whose push arrived during the freeze, with a receive time far past its timestamp. Only the burst's latest frame reflects the server's current inbox.
5. **"On load and on becoming visible"** is `noteVisible()` (visibilitychange visible and pageshow, which also fires on load): it calls `noteReturn()`, which drops any snapshot received before it and cancels a pending sweep, so only a frame received afterwards (on the resumed, probed or new connection) can close anything. At load the closer starts with no snapshot, so nothing acts before the first real frame.
6. **Permission and support guards.** `browserNotifications` returns nothing without `navigator.serviceWorker`, without the Notifications API, without `granted` permission, or without a registration; a throwing list or `close()` is swallowed. No new error or user-visible state.
7. **Manual check scope.** The live two-device case (answer on another device) could not be exercised here (no subscribed device, no shipmates server). The browser check drove the real service worker's notifications in headless Chromium through the same `answeredNotificationCloser` instance the page uses; see the done record.
