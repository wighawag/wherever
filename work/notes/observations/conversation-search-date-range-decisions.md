# conversation-search-date-range: in-scope decisions (2026-11-24)

Decisions taken while building task `conversation-search-date-range`, for the reviewer and the human to ratify or reverse.

1. **Range values and storage.** `SearchRange` is `'any' | '24h' | '7d' | '30d'` (`web/src/lib/core/search-range.ts`, `SEARCH_RANGES` in display order with labels "Any time", "Last 24 hours", "Last 7 days", "Last 30 days"). Stored under `wherever-search-range`, named after the sibling `wherever-search-include-closed`. Any time is stored as ABSENT (the key is removed), mirroring how "Include closed" off removes its key; an unknown stored value reads as Any time. Alternative: store `'any'` explicitly; rejected for symmetry with the existing setting. Touches only this panel.
2. **Separate module, not search-request.ts.** The range lives in its own pure module `search-range.ts` rather than being folded into `search-request.ts` (which holds "Include closed"); `SearchRequest` only gained `since?: string`, so the request builder stays ignorant of ranges and clocks. Alternative: put `rangeToSince` in `search-request.ts`; rejected to keep the clock-dependent logic separately testable.
3. **Whitespace-only `since` is "empty".** `parseSince()` trims, so `since=%20` means no bound (same as absent / empty), rather than an error. The task says "absent or empty means no bound"; trimming is the same reading `q` already gets.
4. **Error wording.** An unparseable `since` answers `status: 'error'`, `message: "Invalid \`since\`: \"<value>\" is not a parseable date (use ISO 8601)."`. The panel already renders `error` messages verbatim. The web never sends a bad value (it only sends `toISOString()` output), so this is for API callers.
5. **Unbounded requests do not send `since` to memonaut at all** (the key is omitted, not passed as `undefined`), so Any time is byte-for-byte today's call.
6. **Re-run on range change: verified by code reading, not by a browser session.** No browser was available to the build agent, so the "checked by hand" criterion is covered by reasoning: `changeRange()` and `toggleIncludeClosed()` now share `rerunNow()`, which clears and nulls `debounceTimer` before running (exactly as before for Include closed), returns early below `MIN_QUERY`, and calls `run()`, which goes through `searchConversations()`'s abort/supersede path. Belt and braces: `run()` computes `since` from the CURRENT `range` when it executes, so even a debounce that somehow fired late would use the new range, never the old one. Selecting the already-active range is a no-op (no re-run). A human should still click through once (type, change range within 250 ms, confirm one request with the new `since`).
7. **Placement.** The selector is a compact `<select>` in the same controls row as "Include closed", after it, styled like the row's 10 px muted text, with a visually hidden "Date range" label and a tooltip.
