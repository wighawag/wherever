# Decisions taken while building `channel-seam-notify-and-web-push` (2026-10-30)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/assistant-channels.ts` (module JSDoc, `ChannelDispatcher`), `server/src/web-push.ts` (module JSDoc, `resolveVapidSubject`, `ensureKeys`, `notify`), `server/src/assistant-tools.ts` (`AssistantSessionHooks.notify`, `resolveNotifyTarget`, `notifySource`), `server/src/session-pool.ts` (`clearQueuedMessages`, the `assistantWebPush` / `publicUrl` config keys), `server/src/index.ts` (wiring, `/push/*` routes), `web/src/lib/core/notifications/index.ts` (`openNotificationTarget`). Documented in `CONTEXT.md` "The channel seam, `assistant_notify` and Web Push".

1. **Dependency-free sender.** RFC 8291 (`aes128gcm`) and RFC 8292 (VAPID ES256) are implemented with `node:crypto` instead of the `web-push` package. The sibling `push-notification-server`'s sender is NOT dependency-free (it wraps `@block65/webcrypto-web-push` / `webpush-webcrypto`), so it was not borrowed either. `pnpm-lock.yaml` and `pnpmDepsHash` are untouched (ADR 0008). The encryption is pinned by RFC 8291's own test vector in `server/test/web-push.test.ts`.
2. **Web Push is on by default while the assistant is active**; `assistantWebPush.enabled: false` turns it off. Rationale: nothing is sent or written until a device opts in through the settings toggle, so the toggle is the real opt-in. Alternative: off unless listed in a channel list. Touches `telegram-token-and-pairing`, whose text says Telegram is "enabled per the config's channel list": no such list exists yet; that task may introduce one, and should then decide whether `webpush` joins it (this key would become its per-channel options).
3. **New config keys `assistantWebPush` (`enabled`, `subject`) and `publicUrl`.** The task says the VAPID subject defaults "from the configured public URL", but no public-URL key existed; `publicUrl` (top level, general, not assistant-prefixed) is added for that and for the links `telegram-conversation` sends "when the wherever public URL is configured". `assistantWebPush` follows the `assistant*` prefix of `assistantFolder` / `assistantScheduleGraceMinutes`.
4. **VAPID subject fallback**: `assistantWebPush.subject` (a `mailto:` or http(s) URL), else the ORIGIN of `publicUrl`, else `https://wherever.dev`. A push service only uses it as an operator contact, so a value that always validates beats refusing to push. An invalid configured subject is warned about and skipped.
5. **Keys on first use, never replaced.** The keypair is generated by the first `GET /push/vapid-public-key` (or a send), not at start, so an active assistant nobody subscribes to writes nothing. An unreadable `assistant-vapid.json` is never overwritten (every subscription is bound to the public key): the request fails naming the file.
6. **State files** at the state-dir root beside `assistant-session.json`: `assistant-vapid.json` and `assistant-push-subscriptions.json`, both mode 0600 (private key; each subscription's auth secret), atomic tmp + rename.
7. **Routes**: `GET /push/vapid-public-key`, `GET /push/subscription?endpoint=`, `POST /push/subscription` (upsert by endpoint), `DELETE /push/subscription {endpoint}`. They exist (and join the token gate) only while Web Push runs; otherwise `/push/*` falls through to the static handler exactly like any unknown route (tested). `DELETE` was added to the global CORS `Access-Control-Allow-Methods`. Subscription endpoints may be `http:` as well as `https:` (browsers always give https; tests and self-hosted push services use http).
8. **Status shape**: `assistant.webPush = { enabled, publicKey (null until generated), subscriptions }`, only while active. "This device subscribed" cannot be known server-side without the endpoint, so the web computes it (`isThisDeviceSubscribed`: a browser subscription the server confirms through `GET /push/subscription`).
9. **`assistant_notify` is registered only while ACTIVE** (`AssistantSessionHooks.notify` set only then), per the task's acceptance criteria and its forward-pointer, unlike the schedule tools. Between registration and the channels starting (a short window at boot) it answers "the assistant channels are still starting".
10. **Tap target fallback**: a `jobId` that names no job, or a job without `originSessionId` (hand-written), falls through to the calling session instead of failing; the tool result says so. A notification is never refused over its tap target.
11. **`source` = a FOLDER name**: the job's `originCwd` basename when the notify is about a job (given or the caller's own isolated job), else the calling session's folder basename. Session names were not used (mostly unset, and not readable for non-resident sessions).
12. **The push title is `<source>: <title>`** (the declarative payload has no separate source field), mirroring Telegram's planned `🔔 <source>: <title>`.
13. **Notify succeeds when at least one channel delivered.** A Web Push channel with zero subscriptions, or whose every push failed, is a failed delivery; so with Web Push as the only channel and no device subscribed, `assistant_notify` returns an `isError` (the agent learns nothing reached the user). With no channel at all: `NO_CHANNEL_ERROR`.
14. **Channel name = routing origin**, and a destination `name:<sub>` (e.g. a future `telegram:<chatId>`) also belongs to channel `name`. Web Push is named `webpush` and never originates a message.
15. **`!` is refused at the dispatcher** for every channel's inbound message (defense in depth for story 16; `telegram-conversation` still owns the user-facing explanation). Inbound `files` are accepted in the type but not forwarded yet (`telegram-files`).
16. **Dropped-message origins**: `SessionPool.clearQueuedMessages` now also returns `origins` (aligned by index with pi's texts, paired from the NEWEST end like the settle trim, null when unknown), carried in `DroppedMessages.origins`. The dispatcher reports each text to the channel of its origin; web (`none`), scheduler and unknown origins are reported to nobody.
17. **Push options**: TTL 24 h, `Urgency: high` (a deliberate notification should wake the device), one record (RFC 8188 record size 4096).
18. **`ASSISTANT_TOOL_TEXTS` now lists five tools** (the four plus `ASSISTANT_NOTIFY_TEXT`); the four alone are `ASSISTANT_SCHEDULE_TOOL_TEXTS`. `cli-assistant-tool-twins` lists exactly these five.
19. **Foreground click**: a target on this page (same origin, and the same path or `/`) with a hash sets `location.hash` (fires `hashchange`); anything else is `location.assign`. `pushState` is no longer used there.
20. **Web placement**: the "Assistant notifications" toggle sits below Connection Settings in the settings panel, shown only while `active` and `webPush.enabled`; the service worker routes `/push/` online-first like the other API paths.
21. **Changeset bump is `minor`** (new user-visible tool, setting and config keys).
