# Decisions taken while building `assistant-scheduler` (2026-10-30)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/assistant-cron.ts` (module JSDoc: parser choice, DST), `server/src/assistant-schedule.ts` (module JSDoc: file shape; `planJob`, `PlanOptions.since`, `ScheduleStore`, `UserTimezone`), `server/src/assistant-scheduler.ts` (module JSDoc; `sinceFor`, `drainInline`, `isIdle`, `formatScheduledPrompt`), `server/src/assistant-controller.ts` (`clearAfterAbort`), `server/src/index.ts` (`scheduleGraceMs`). Documented in `CONTEXT.md` "The assistant scheduler".

1. **Hand-written 5-field cron parser, no library.** A new dependency changes `pnpm-lock.yaml` and so the Nix `pnpmDepsHash` (ADR 0008) for about 200 lines, and the zone is supplied per evaluation anyway (a follows-the-user job is re-evaluated in the user's current zone). Considered: `croner` (zero-dep, timezone-aware), `cron-parser` (pulls in luxon). Syntax: `*`, lists, ranges, steps, month/weekday names, `@yearly`/`@monthly`/`@weekly`/`@daily`/`@hourly` macros, Vixie day-of-month OR day-of-week rule.
2. **DST semantics.** A local time in the spring-forward gap fires once at the instant the gap ends; a local time that occurs twice fires at its first occurrence only (so a sub-hourly job skips the repeated hour). Chosen because it keeps local-to-instant mapping monotone. Rejected: Temporal's "compatible" gap shift (not monotone).
3. **File shape `{ "jobs": [...] }`.** A missing file is empty; any other top-level shape (bad JSON, a bare array) makes the whole file unreadable: nothing fires, `list()` reports `fileError`, and writes refuse with `ScheduleFileError` rather than replace a file the user may be mid-edit on. Unknown keys (top level and per job) are preserved by writes and ignored by the scheduler. `name` and `enabled` are REQUIRED (no defaults); a duplicate id makes the later entry invalid. Touches `assistant-schedule-tools-server` (its tools write and list this format).
4. **When a missed run counts.** The base of a recurring job is its newest run entry's `scheduledFor`. With no run yet it is when THIS process first saw the job, and a re-enable or an edit of `cron`/`at`/`tz` resets it to then (in memory only; nothing is written into `schedule.json`). So a job never catches up on a run from before it existed or was enabled. Accepted cost: a brand-new job whose first occurrence falls while the server is down is not caught up on restart (there is no run entry to measure from). Alternative: persist a "first seen" per job in the state dir.
5. **The grace rule applies on every tick, not only at startup.** A late tick (laptop sleep, a blocked loop) follows the same "latest missed run fires once if within the window, else skipped and recorded" rule.
6. **Config key `assistantScheduleGraceMinutes`** (top-level beside `assistantFolder`, minutes, default 60, read at start like `assistantFolder`). A non-number or negative value logs a warning and uses the default. Alternative: a nested `assistant: {}` object (none exists yet).
7. **Run log vocabulary.** `outcome` is `fired` | `failed` | `refused` | `skipped`. The `fired` entry is written at DISPATCH (a server send resolves only after the whole run), and a send that later rejects appends a `failed` entry for the same occurrence. The isolated job-to-session mapping is read back from the log's `sessionFile`, so it survives restarts.
8. **Isolated jobs use the same text as inline ones** (`[schedule:<name>] ...`, `/` prompts verbatim). The task specified the format for inline only; the prefix tells the job agent it is a scheduled job. Missing origin parts are omitted (no parenthesis when neither is set).
9. **Inline delivery is one job per exchange,** queued in memory (not persisted; after a restart the grace rule re-decides). A job removed or disabled while it waits is dropped without a run entry. Busy = streaming, OR a run seen started without its settle, OR our own send not yet finished, OR pi's queue non-empty (new `SessionPool.getQueuedMessageCount`). A CLI-bridge send that never produced `agent_start` (an extension command handled it, invisible to the server) stops blocking after 60 s.
10. **The abort clear is unconditional for the current assistant session.** On ANY aborted `agent_settled` of the current pointer session (whether or not a job is pending) the controller clears pi's leftover queue and records it (`DroppedMessages.reason` gains `'aborted'`). User-visible: in the assistant session, messages still queued when a turn is aborted are dropped (and recorded) instead of being delivered after the next prompt. Touches `channel-seam-notify-and-web-push` (reports `onDropped` batches, now with two reasons). CLI-bridge sessions: nothing to clear (queues invisible).
11. **Timezone state** `<stateDir>/assistant-timezone.json` `{ timezone, updatedAt, history }` (history bounded to 200), written once at `start()` (system zone, source `system`). `onTimezoneChange` exists but is NOT wired to `pushAssistantInfoChanged` here; `assistant-schedule-tools-server` wires it with the `assistant_info` timezone.
12. **Hand edits are picked up by re-reading per tick** (at most 30 s apart, sooner when a run is due; `unref`'d timer), not a file watcher.
13. **`!` refusal matches the pool's own test** (`prompt.trimStart().startsWith('!')`), so `  !!cmd` is refused too.
14. **Changeset bump is `minor`** (new user-visible feature and config key).
