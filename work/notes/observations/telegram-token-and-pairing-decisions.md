# Decisions taken while building `telegram-token-and-pairing` (2026-10-31)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/telegram-token.ts` (module JSDoc), `server/src/telegram-pairing.ts` (module JSDoc, `CODE_ALPHABET`), `server/src/telegram-channel.ts` (module JSDoc, `handle`), `server/src/session-pool.ts` (the `assistantTelegram` config key), `server/src/index.ts` (wiring, `telegramStatus`, `/telegram/repair`), `web/src/lib/core/telegram-settings.ts`, `web/src/lib/components/AssistantTelegramSettings.svelte`. Documented in `CONTEXT.md` "The Telegram channel: token, long polling and pairing".

1. **No channel LIST: a per-channel `assistantTelegram.enabled`.** The task says Telegram is "enabled per the config's channel list", but no list exists (the `channel-seam-notify-and-web-push` decisions note, item 2, flagged this for this task). Web Push already has `assistantWebPush.enabled` (default on). A list such as `assistantChannels: ["telegram"]` would either have to include `webpush` (breaking the default-on Web Push of installs that never listed it) or exempt it (one list meaning "opt-in channels except one"). So Telegram gets the parallel per-channel block `assistantTelegram: {enabled, token, userId, apiBaseUrl}`, OFF unless `enabled: true`. Alternative: a channel list, with `assistantWebPush` / `assistantTelegram` becoming per-channel options; reversible later by reading a list and falling back to these flags. Touches `telegram-conversation`, `telegram-files` and any future WhatsApp channel (they should follow the `assistant<Channel>` block pattern).
2. **`assistantTelegram.apiBaseUrl`** (default `https://api.telegram.org`). It is how the spawned-server tests mock the Bot API at HTTP, and it is also real configuration (a self-hosted `telegram-bot-api` server). Alternative: an env var only for tests; rejected because a test-only switch in the server is worse than a documented, legitimate key.
3. **An unreadable or empty token file does NOT fall through to `assistantTelegram.token`.** Same reasoning as ADR 0007 for its own token file: the operator asked for the file, so a missing one is a failed secret render to report, not a cue to use an older config value. Missing token entirely (enabled, no source) also disables Telegram loudly. Set-but-blank variables warn and count as unset (ADR 0007).
4. **The env scrub runs ALWAYS, in `parseArgs`,** beside the auth-token scrub, before anything is spawned, whether or not Telegram is enabled (the task allows it). The values are captured there; the FILE is read only while active and enabled.
5. **The one-time code is in MEMORY only** (8 characters of `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, about 40 bits, a new code each start). Persisting it would write state while unpaired; a restart simply shows a new code in the web. No rotation after wrong attempts: at Telegram's per-chat message rate 40 bits is out of reach, and rotation would let a stranger invalidate the code the user is reading. Comparison is case-insensitive and constant-time.
6. **Unpaired: everything but the right `/pair <code>` is ignored, including `/start` and wrong codes,** never answered (no "the bot is live" signal, no wrong-code oracle). Only PRIVATE chats count; group messages are ignored even from the paired user (groups are out of scope). Bot senders are ignored.
7. **A paired user's non-command text is forwarded to `ctx.onUserMessage`** (origin `telegram`) without awaiting it (the send resolves at the end of the turn, and polling must go on). So messages already reach the assistant session in this task; Telegram replies, the steer marker, `!` explanations, `/new`, `stop` and ordering for steers are `telegram-conversation`'s. Alternative: drop them until then, rejected because the offset advance would lose them silently.
8. **The polling offset is stored with the bot id** (`{botId, offset}`, the token's numeric prefix) and an offset of another bot is ignored, because update ids are per bot and a stale high offset would skip the new bot's updates. It is written after EACH handled update (at-least-once: a crash between handling and writing replays at most one update). The pairing is not bound to the bot (it names a person).
9. **State files** at the state-dir root beside the other assistant files: `assistant-telegram-offset.json` and `assistant-telegram-pairing.json`, mode 0600, atomic tmp + rename. Re-pair removes the pairing file.
10. **Failure policy:** 401 / 404 from the Bot API (wrong token) stop polling and report `state: 'error'` (fix and restart); anything else is retried, 1 s doubling to 60 s, honouring `retry_after`. Error text has the token redacted.
11. **Re-pair route `POST /telegram/repair`**, token-gated and present only while the channel runs (else an unknown route, like `/push/*`); 409 while the user id comes from the config (`CONFIGURED_USER_REPAIR_ERROR`). The web hides the Re-pair button for a configured id. A malformed `assistantTelegram.userId` is warned about and ignored (pairing by code then applies).
12. **Status shape** `assistant.telegram` (only while active): `{enabled: false, state: 'disabled'}`, `{enabled: true, state: 'disabled', error}` (no usable token), else `starting` / `unpaired` (`code`, `bot`) / `paired` (`user: {id, name?, source}`, `bot`) / `error`, plus an optional transient `error` (e.g. a 409 while another poller holds the bot). The pairing code rides `/config`, which is behind the API token.
13. **Live update by polling, not a new frame:** the settings section refetches `/config` every 3 s while `unpaired` / `starting` and stops once paired. Alternative: add `telegram` to the `assistant_status` WS frame; rejected for now to keep the protocol unchanged (the section is only open while the user is pairing).
14. **Web placement:** "Assistant on Telegram" sits below "Assistant notifications" in the settings panel, shown while `active` and `telegram.enabled` (also when enabled but disabled by a token error, to show the error).
15. **Test harness:** `server/test/harness.ts` gained `output()` (the server's stdout + stderr) so the "logs loudly" and "logs nothing" criteria are asserted; `server/test/fake-bot-api.ts` is the Bot API fake (injected `fetch` or a local HTTP server).
16. **Changeset bump is `minor`** (a new user-visible channel, settings section and config key).
