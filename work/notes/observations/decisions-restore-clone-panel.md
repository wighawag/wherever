# Decisions taken while building `restore-clone-panel` (2026-09-09)

In-scope choices the task did not specify, recorded here (per CLAIM-PROTOCOL) so a reviewer can ratify or reverse them rather than reverse-engineer them. None met the ADR gate on its own (each is cheap to reverse and sits under the decisions `docs/adr/0009` and `0010` already record), but each is visible to another task, to a user, or to the next reader of the vocabulary.

1. **A restore IN FLIGHT is reported as `folder_missing`, not as a new state.** DRIFT found by the reconnect test: `git clone` creates the target directory in its first breath, so `readSessionMeta`'s `stat` says "present" for the whole of a multi-minute clone, and a client loading in that window (the reconnect and second-device criteria of this very task) was handed a live agent pointed at a HALF-CLONED tree -- exactly the silent breakage `folder-missing-read-only-state` exists to replace. `session_load` therefore ORs the `stat` with "a restore job is `running` for this cwd". The state's meaning widens from "the folder does not exist" to "the folder is not usable as a working folder", with two producers and one remedy. Alternative considered and rejected: a separate `folder_restoring` state/frame, which forks the concept, doubles the client state and the UI branch, and buys nothing -- the cure (restore, then reload) and the rendering (the panel) are identical. Touches `missing-folder-badge-in-session-list` (a badge computed from existence alone will show "present" mid-clone) and `new-session-clone-via-registry`. Pinned in `CONTEXT.md`.

2. **Candidates are fetched from `GET /remote-candidates`, not carried on the `folder_missing` frame.** The task body says the frame is extended "to carry the resolved SSH candidates AND any restore job", but `restore-remote-candidates` deliberately landed them as an on-demand endpoint (its decision 1, which names this task as the consumer) because the probe shells out to a provider CLI and the frame is on the session-load path. Followed the dependency's landed shape: the frame carries `job` only, and the panel fetches candidates once, when it opens for a folder.

3. **Four server frames, not two.** The task names "restore progress and restore completion". Two more were needed and are per-requester answers rather than broadcasts: `restore_started` (carries `outcome: 'started' | 'joined'` and the url really in flight -- the acceptance criterion "the second Clone tap joins it and is told the URL actually in flight" cannot be met by a broadcast that says nothing about whose request it answers) and `restore_rejected` (a refusal happens before any job exists, so there is no id and no completion coming; folding it into `restore_complete` would need a synthetic failed job, i.e. a lie about a job that never existed). `restore_complete` deliberately carries all three terminal states rather than splitting `done` / `failed` / `cancelled` into separate frames.

4. **`restore_start` carries `action: 'clone' | 'create'` and `gitInit`, and the server passes BOTH kinds through to the registry, but only Clone is offered in the UI.** The task's own wording asks for the action on the frame, and the registry is deliberately one state machine for both kinds, so a clone-only frame would have to be widened by the next task. `restore-create-folder-action` owns the Create UI, the git-init default and their tests; nothing here pre-empts that except the frame's shape.

5. **Cancel (and start) are NOT restricted to a client whose folder matches the path.** A derived match gates who RECEIVES broadcasts, but neither request is refused for a non-matching client. Rationale: the job is server-owned and path-keyed precisely so the device that started it may be gone, and any authenticated client can already drive a clone through `session_new`, so a match requirement would add a new user-visible refusal (a panel that raced a session switch would be told no) without adding a security boundary. Safety stays where the registry put it: inside the home directory, empty leaf, URL allowlist, argv arrays. Alternative considered: refusing a non-matching `targetPath` with `restore_rejected`.

6. **The registry is a module-level singleton in `server/src/index.ts`**, not threaded through `handleWSMessage` like the session pool. One server process owns one path-keyed registry (`docs/adr/0009`); constructing it is inert. Touches `new-session-clone-via-registry`, which must drive this same instance rather than making a second one.

7. **The send refusal is re-worded while a restore runs**: "is still being restored ... wait for the restore to finish, then reload" instead of "does not exist on this machine ... restore the folder". A user-visible message default, introduced because decision 1 made the old wording inaccurate for a folder that is being cloned right now.

8. **Tests slow the clone with a `post-checkout` hook injected through the SERVER's `GIT_TEMPLATE_DIR`**, so "while the job is RUNNING" assertions (reconnect, second device, cancel) are deterministic rather than racing a local clone that finishes in milliseconds. The delay lands after git's own progress output, so the frames under test are unaffected, and it exists only in the test harness's environment: production clones pass no template dir.
