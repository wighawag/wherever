# Decisions taken while building `restore-remote-candidates` (2026-09-09)

In-scope choices the task did not specify, recorded here (per CLAIM-PROTOCOL) so a reviewer can ratify or reverse them rather than reverse-engineer them. None met the ADR gate (each is local and cheap to reverse), but each is visible to another task, to a user, or to a later reader of the vocabulary.

1. **The endpoint is `GET /remote-candidates`, a sibling of `/check-remote-repo`, and candidates are NOT pushed on the `folder_missing` frame.** `CONTEXT.md` says "later work extends that frame with remote candidates", which would put a provider-CLI `execFileSync` on the SESSION-LOAD path (and on every session load of a missing folder, including the session browser's). The task's own instruction is explicit that the probe "must never run per keystroke" and belongs on an on-demand endpoint, so the frame stays cheap and the panel fetches when it opens. Touches `restore-clone-panel` (it must call this endpoint rather than read the frame) and the `folder_missing` frame's shape. Name chosen over `/restore-candidates` to avoid re-meaning `restore`, which `CONTEXT.md` pins to the ACTIONS that cure the state (the clone/create jobs); what this endpoint returns is a remote-repo candidate, which is what `/check-remote-repo` next door already talks about.

2. **The provider probe is INJECTED, not imported** (`resolveRemoteCandidates(path, rules, probe?)` in `server/src/remote-candidates.ts`; `index.ts` passes `detectRemoteRepo`). Alternative considered: importing `detectRemoteRepo` directly, which would drag the session pool (and the pi agent dependency) into a module that is otherwise a pure function, and would make "the tests need no provider CLI" a matter of discipline rather than structure. Omitting `probe` resolves the path convention alone. Same standalone posture as `restore-jobs.ts`.

3. **Rule matching is CONSOLIDATED into `matchRemoteRepoRule`** in the new module, and `index.ts` deleted its local `repoRuleMatches`; `/check-path` and `/check-remote-repo` now go through the shared one. Alternative considered: a third copy of the tilde-expanding matcher. Touches those two endpoints (behaviour identical: same expansion, same invalid-pattern-is-a-non-match). NOTE, deliberately NOT fixed here: `session-pool.ts` still matches rules with a bare `new RegExp(r.pattern)` in two places (the create-session clone probe and the remote-repo provisioning), so a `~/...` pattern does not match there — see `work/notes/observations/remote-repo-rules-untilded-in-session-pool.md`.

4. **The known host tokens are `github`, `codeberg`, `gitlab`, plus any token that is ALREADY a dotted hostname.** `gitea` and `forgejo` are deliberately absent even though they are valid `remoteRepoRules` providers: they name SOFTWARE, not a host, so there is no single hostname to map them to and a self-hosted instance is written as its own dotted folder (`git.example.com/owner/repo`). An unknown token yields NO candidate rather than a guessed `github.com`, per the task's "no candidate rather than a wrong one". User-visible: someone whose tree uses `~/dev/gh/...` gets an empty field and pastes a URL.

5. **A folder named `repo.git` derives `git@host:owner/repo.git`, not `repo.git.git`.** Small, but it is the shape a mirror/bare-style checkout takes on disk.

6. **A probe result that is not an SSH URL is DROPPED, not offered.** ADR 0010 forbids synthesising an HTTPS candidate; this makes it hold even if a provider CLI is configured to hand back an HTTPS clone URL. The derived candidate still stands in that case, so the field is not left empty for it.

7. **De-duplication keeps the probe as the source** when both sources produce the identical URL (the common case for the owner's own namespace laid out by convention), so the list stays one entry rather than two identical ones.
