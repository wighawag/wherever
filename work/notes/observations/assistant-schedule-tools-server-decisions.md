# Decisions taken while building `assistant-schedule-tools-server` (2026-10-30)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/assistant-tools.ts` (module JSDoc, `scheduleAdd`, `isAssistantFolderCwd`, `SET_TIMEZONE_SOURCE` / `WEB_TIMEZONE_SOURCE`), `server/src/assistant-tool-text.ts` (module JSDoc), `server/src/session-pool.ts` (`setAssistantSessionHooks`, `composeServerAgentParts`), `server/src/index.ts` (the hooks, `onClientTimezone`, `broadcastAssistantStatus`), `web/src/lib/core/timezone-report.ts`. Documented in `CONTEXT.md` "The assistant tools and the timezone line".

1. **`mode` is REQUIRED on `assistant_schedule_add`** (no default). Choosing a default between inline and isolated is a behaviour decision the AGENTS.md brief deliberately leaves to the agent ("delegate long work to isolated"). Alternative: default `inline`. Touches `cli-assistant-tool-twins` (same schema).
2. **A tool-added job is always `enabled: true`, and its `id` is generated** (`job-<8 hex>`, the store's existing rule). There is no `enabled` or `id` parameter: disabling is a hand edit of `schedule.json`, and to change a job the agent removes it and adds the new version (said in the remove tool's description). Alternative: an `assistant_schedule_update` tool (not in the spec's tool list).
3. **A prompt starting with `!` is refused at ADD time** (an `isError`, nothing written), on top of the scheduler's run-time refusal, so the agent learns immediately instead of seeing a `refused` run later. New refusal, same rule as the scheduler (`trimStart().startsWith('!')`).
4. **The tool set is the same whatever the lock says.** Registered while `assistantFolder` is CONFIGURED; a server whose assistant is not active (lock `refused` or `error`, or the scheduler not started yet) answers `The wherever assistant is configured but NOT active on this server (folder lock <state>): <lock message>`. This follows the task text over the forward-pointer's `active` gate for registration, as the forward-pointer itself asks.
5. **The timezone-line extension is added only to sessions built in the assistant folder or its `jobs/`** (not to every session with an internal cwd check), compared by `path.resolve` equality like the controller's pointer check (so a symlinked `assistantFolder` has the same limitation already noted in `assistant-folder-symlink-cwd-mismatch.md`). Only `jobs/` itself, not deeper subfolders. It appends nothing while no timezone is known (not active). It is placed right after the conversation-mode extension; both append to the prompt the event carries.
6. **Injection seam: `SessionPool.setAssistantSessionHooks({ folder, access })`**, set once at start in `main()`; `access()` is read at every tool call and returns the scheduler only once it has started. `composeServerAgentParts` is exported so the "unset = byte-identical" rule is a pure test (identity of every extension factory, tool names `attach_file`, `say`). The caller (`sessionId`, `cwd`) comes from the session's own `SessionManager` and cwd at build time, never from tool arguments.
7. **New WS message `client_timezone {timezone}`**, sent by the web on EVERY `connected` frame (each new socket, so also on reconnect), to any server (an older one drops it). Applied only while the assistant is active and only when it differs; history source `web`. Consequence worth knowing: a web connect from the browser's zone overrides a zone the user set through the assistant ("I'm in Tokyo" while the laptop says Paris), and two devices in different zones alternate the setting; the task asks for exactly this behaviour. An unknown zone is logged and ignored.
8. **History sources:** `assistant_set_timezone` for the tool, `web` for the report (the scheduler's `system` stays the initial one).
9. **`assistant_status` gains an optional `timezone`**, and is now also broadcast on every timezone change (not only on pointer moves), carrying the pointer too. The web's `applyAssistantPointer` keeps the known zone when a frame has none (older server). `GET /config` `assistant` carries `timezone` only while active (absent otherwise, like the pointer fields), and `assistant_info` returns `timezone: null` when not active.
10. **The web shows the timezone in the sidebar's Assistant entry** (a small muted label, and in its tooltip), which only exists while active, so all assistant UI stays hidden with the feature off.
11. **Test seam added to the fake LLM: `queue(...behaviors)`**, one-shot behaviors used before the sticky `setNext` one, so a test makes exactly one tool call without racing the follow-up request (a duplicated `assistant_schedule_add` would add two jobs).
12. **Changeset bump is `minor`** (new user-visible tools and behaviour).
