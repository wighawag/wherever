# Decisions taken while building `new-session-clone-via-registry` (2026-09-10)

In-scope choices the task did not specify, recorded here (per CLAIM-PROTOCOL) so a reviewer can ratify or reverse them rather than reverse-engineer them. None met the ADR gate on its own -- each is cheap to reverse and sits under `docs/adr/0009`, which already records that both entry points share one registry and that only this one continues into creation. Each is visible to another entry point, to a user, or to the next reader.

1. **The clone URL is resolved SERVER-side (the provider probe), never taken from the client.** JSDoc at `cloneForNewSession()` in `server/src/index.ts`. The create flow has no editable URL field -- the dialog only asks "clone the one we found, or create a new one?" -- so accepting a client-supplied URL would introduce a new authority nobody asked for, and would be the one asymmetry with the restore panel that is NOT justified by the UI. The probe (`matchRemoteRepoRule` + `detectRemoteRepo`) is the same one the dialog itself asked through `/check-remote-repo`, so the URL cloned is the URL the user was shown. Alternative considered: send the `sshUrl` the dialog already holds on `session_new` (one fewer probe, and testable without a fake `gh`), rejected on the authority grounds above. Touches `/check-remote-repo` and the restore panel's editable field, which stays the deliberate exception.

2. **The path-CONVENTION candidate is deliberately not used here.** Only the probe result is cloned; `resolveRemoteCandidates()` (probe, then `<host>/<owner>/<repo>` derivation) is the restore panel's resolver and stays there. A derived URL is advisory and is offered to a human who can edit it; feeding an unprobed guess into a create with no URL field would clone (or, more likely, fail against) a repository nobody confirmed exists. When the probe finds nothing the clone is SKIPPED and an ordinary create follows, which is exactly what the deleted synchronous path did.

3. **A failed, rejected or cancelled clone is reported on `session_error`, the create's own channel** (comment at the `session_new` handler). The restore panel owns its outcome and stays on screen; a create has no panel to stay in, so the mapped cause has to arrive on the channel that ends the create -- otherwise a client that does not render restore frames would sit on a blocking overlay forever. The `restore_complete` frame with git's raw stderr is broadcast beside it, so nothing is lost. User-visible message default; touches the `restore_rejected` frame, which is deliberately NOT sent for this path (there is no offer-state to return to).

4. **`SessionPool.createNewSession` loses its `cloneRemote` parameter entirely**, rather than keeping it as a pass-through (note at the deleted helper in `server/src/session-pool.ts`, and `CONTEXT.md`). The pool no longer knows how to clone at all, which is what makes "one clone implementation" structural instead of a convention. Consequence checked: the `cloned` flag that used to suppress git-init and remote-creation is gone, and both are already guarded by `.git`-exists / `hasOrigin`, which a fresh clone satisfies. Touches `POST /session/new` (decision 5) and any future caller of the pool.

5. **`POST /session/new` keeps `cloneRemote` and takes the same registry branch, awaiting the job.** Documented at the call site and in `docs/USAGE.md`. Dropping the flag would have been a silent API removal; leaving it on a pool that can no longer clone would have been a silent no-op. It gains recursion and the mapped failure; having no progress channel, it simply waits, which is what an HTTP caller already expected. WebSocket clients watching that folder still get live frames, because the broadcast is derived from the path.

6. **The client ADOPTS the job into `WhereverState.restore` with `forSessionCreate: true`, and disarms the create watchdog while it runs** (JSDoc in `client/src/types.ts`, comments at both frame handlers in `client/src/client.ts`). A new field rather than inferring "a restore with no folder-missing session": the ENDING differs (no Reload; the server continues by itself), so the difference is real state, not a rendering accident. On `restore_complete` with `done` the client re-arms `creatingSession` and the watchdog for the last, ordinary step the server is already performing -- which also keeps `session_created`'s superseded-reply guard (`isRequestedCreate` needs `creatingSession`) working. Alternative considered: leave `creatingSession` true throughout, rejected because the blocking overlay plus its 25s watchdog is exactly what the task exists to remove.

7. **The progress display is EXTRACTED into `web/src/lib/components/RestoreProgress.svelte`** and used by both the panel and the create overlay, rather than duplicated. "The same progress display" is an acceptance criterion, and honesty (real percentage vs explicit indeterminate, submodules scoped separately) is then decided in one place. The create overlay keeps a Cancel button, which needs no new mechanism: the job is path-keyed, so the ordinary `restore_cancel` settles it and thereby abandons the create.

8. **The create handler records the target as the client's `pendingCwd` before starting the job.** That is what puts a client with no session yet in scope for the DERIVED broadcast, reusing the existing subscription rule rather than adding a per-socket registration for this path. It is cleared on the failure return and overwritten by the real cwd on success.

9. **Tests put a fake `gh` on the SERVER's PATH.** The probe shells out, so a protocol-seam test of this path needs one; the fake answers `gh repo view` with a local `file://` fixture, keeping the whole round trip free of network, SSH key and provider account, exactly as the panel's tests are. It lives only in the harness's environment.
