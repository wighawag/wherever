# Decisions taken while building `scheduler-catches-up-a-missed-first-run` (2026-10-31)

Code sites: `server/src/assistant-schedule.ts` (`FirstSeenStore` JSDoc, `FIRST_SEEN_FILE`, `jobTimeSpec`), `server/src/assistant-scheduler.ts` (`track`, `prune`, `sinceFor`). Documented in `CONTEXT.md` "The assistant scheduler" (the "First-seen state" bullet). Reverses the accepted cost of `assistant-scheduler` decision 4 ([assistant-scheduler-decisions.md](assistant-scheduler-decisions.md)).

1. **File name and shape.** `<stateDir>/assistant-first-seen.json` = `{ "jobs": { "<id>": { firstSeen, enabled, spec: [cron, at, tz], changedAt? } } }`, times as ISO strings (like the run log). Named after the task's own term "first seen" and the sibling `assistant-runs.jsonl` / `assistant-timezone.json`. Alternative considered: `assistant-job-bases.json` (more accurate since it also holds `changedAt`, but a new word for the same concept).
2. **The last-seen `enabled` and time spec are persisted too, so an edit or a re-enable made while the server was down resets the base at the first tick after the restart.** This follows from persisting the comparison state, and keeps the rule "a job never catches up on a run from before it was on / had its current spec". Before this task such a change was invisible across a restart (the new process simply saw the job with its new spec, and a job with runs measured from its last run). Alternative: persist only `firstSeen` / `changedAt` and keep comparing in memory (an edit while down would then catch up on a run of the NEW spec measured from an old run of the OLD spec).
3. **Pruning is skipped while `schedule.json` is unreadable, and an entry present but invalid keeps its base.** Otherwise a half-typed hand edit would persistently reset every job to "from now". Before this task the in-memory `seen` map was cleared in both cases (harmless then, since it was lost on restart anyway). Entries of jobs actually removed from the file are pruned on the next tick.
4. **Degrade rules.** A missing file is silent (first start). An unreadable file, invalid JSON, a missing `jobs` object, or a malformed entry is a `console.warn` naming the file (and the job id for an entry); the affected jobs count from when they are seen now (the behaviour before this task). The next save overwrites a corrupt file (it is server state, not user intent). It is written only when the map changes (a new job, a re-enable, an edit, an `enabled` toggle, a prune), so a start with no jobs still leaves only `assistant-timezone.json`.
5. **One-shots are tracked too** (as before, in memory): an `at` keeps its rules (`planJob` ignores `since` for a dated `at`); an `at: "now"` job's `scheduledFor` is its first-seen time, now persisted.
6. **Changeset bump `patch`,** as the task specifies (a behaviour fix, no new config key).
