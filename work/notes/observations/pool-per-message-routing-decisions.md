# Decisions taken while building `pool-per-message-routing` (2026-10-30)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/reply-routing.ts` (module JSDoc: entry states, take rule, trim, clear), `server/src/session-pool.ts` (`sendUserMessage`, `routeEvent`, `subscribeEvents`, `getReplyDestination`, `onEvent`, `routing`, `cancelSteerQueue`, `clearQueuedMessages`, `handleCliEvent`, `setupEventListeners`). Documented in `CONTEXT.md` "Per-user-message reply routing".

1. **Entries track pi's disposition, and a `started` entry moves to the FRONT of prompt-or-steer.** ADR 0014 says a user `message_end` takes "the head of the matching queue". Taken literally that misattributes after an abort: the abort leaves a steer in pi's queue (its entry kept by the settle trim), and a new prompt into the now-idle session is delivered BEFORE that steer (pi delivers queued steers only after the prompt's first turn; the abort test shows it). `preflightResult('started')` fires before the prompt's user message, so moving that entry to the front keeps matching purely positional. Alternative: the ADR's literal head-take (fails the "aligned after abort" criterion on the next message). Touches nothing outside the pool; refines, does not contradict, ADR 0014.
2. **Which queue a user `message_end` takes from.** The first entry pi already has (started / queued / relayed) in prompt-or-steer, else in followUp, else the oldest remaining entry. pi delivers a started prompt, then steers, then follow-ups; an entry still awaiting its preflight (in pi's input handlers) is not yet in pi's queue, so a delivered follow-up must not take it. The last-resort fallback is ADR 0014's accepted CLI misattribution (a message typed in the terminal takes the head entry, corrected at settle). Alternative: plain "prompt-or-steer head, else followUp head".
3. **Deferred prompts.** `prompt()` returning with no preflight (pi defers a prompt made during `agent_settled` emission) marks the entry `deferred`; it stays matchable and its later preflight updates it. A `deferred` entry still unresolved at the NEXT settle is dropped as stale (the deferred action threw inside pi, which the pool cannot see). Alternative: keep it forever (permanent drift).
4. **Settle trim keeps in-flight sends.** "Trim to pi's queue length, keeping the newest" applies only to entries pi has queued (`queued` / `relayed`); `pending` entries (preflight not yet fired, so not in pi's queue yet) are kept, and stale `started` / `deferred` ones dropped. Without this, a send still in pi's input handlers at settle would be trimmed and its message would take the next entry.
5. **`cancelSteerQueue` / `clearQueuedMessages` drop only what pi had queued** (`queued` / `relayed`), keeping `pending` entries, which pi queues AFTER the clear. `cancelSteerQueue` stays a complete no-op for CLI sessions (criterion). `clearQueuedMessages` does NOT yet return the dropped ORIGINS (`ReplyRouting.clear()` does return them): reporting dropped messages to their channels is `channel-seam-notify-and-web-push`'s, which can extend the port.
6. **Fan-out API and order.** `onEvent` keeps its slot and semantics. New `subscribeEvents(listener) => unsubscribe`, listener `(sessionFile, event, destination)`. Per server event: routing update, `onEvent`, the pool's idle bookkeeping, then subscribers (after the bookkeeping so a subscriber that sends from `agent_end` is not followed by a `scheduleIdleCheck`). Each subscriber is isolated (throw or rejection logged). The pool's own synthetic events (`!` command output, `bash_sudo_prompt`, the CLI-disconnect `session_error` / `agent_end`) now go through the same fan-out (`emitEvent`), with the broadcaster unchanged. Alternatives: an `EventEmitter`; subscribers before the bookkeeping. Touches `channel-seam-notify-and-web-push`, `assistant-scheduler`, `cli-bridge-foundation` (all consume this fan-out).
7. **Origin on the pool send is a 5th positional parameter** (`sendUserMessage(file, text, behavior?, conversationMode?, origin = 'none')`), matching the existing positional style; the controller passes `false` for `conversationMode`. `WEB_ORIGIN = 'none'` is the recorded web origin; a destination of `null` means "no origin at all" (nothing recorded). Consumers should treat both as "not a channel".
8. **CLI settle needs the forwarded `agent_settled`.** The pool empties a CLI session's routing queues on a CLI `agent_settled` event, which the extension forwards only from `cli-bridge-foundation` on. Until then a CLI session's entries are consumed only by `message_end` (no `agent_end` fallback here; `assistant-scheduler` owns that fallback for old extensions). Alternative: also empty at CLI `agent_end`, which fires between chained internal turns and would drop live follow-up entries.
9. **Routing state lifetime.** Keyed by session file, kept across a CLI takeover and the CLI-to-server handoff, dropped with the pool entry (destroy, idle eviction, failed reload), whose pi queues are gone too.
10. **Changeset bump is `patch`** (no user-visible change).
