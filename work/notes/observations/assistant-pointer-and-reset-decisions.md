# Decisions taken while building `assistant-pointer-and-reset` (2026-10-30)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/assistant-controller.ts` (module + method JSDoc), `server/src/session-pool.ts` (`onSessionCreated`, `pinnedSessions`, `clearQueuedMessages`), `server/src/index.ts` (`assistant_open` / `assistant_reset`).

1. **Status shape.** `GET /config` `assistant` gains `currentSessionId` / `currentSessionFile` ONLY while the assistant is active (null until a session exists); with the feature off or refused the payload is byte-identical to before. Alternative: always present (null). Touches every later task that adds status fields.
2. **Pointer file.** `<stateDir>/assistant-session.json` (`{ folder, sessionFile, sessionId, updatedAt }`, atomic tmp + rename), at the state-dir root beside ADR 0015's `assistant-runs.jsonl`. A record whose `folder` differs from the configured one (config changed across a restart) is IGNORED, not migrated. Touches `cli-bridge-foundation` (writes the pointer through the same controller).
3. **A dangling pointer is replaced.** pi writes a session file only once a conversation starts, so a pointer that is neither resident nor on disk (an evicted or pre-restart session nobody spoke in) is replaced by a fresh session on the next open/send, instead of erroring. Nothing is lost: such a session had no content.
4. **Pinning applies to CLI-bridge entries only.** A pinned SERVER session is still idle-evicted (the AC requires the pointer to survive eviction by reloading on the next send). Only the CLI idle-teardown race named in the task is closed. Alternative: pin both (never evict the assistant session's agent).
5. **`send` steers by default while a turn is running** (ADR 0003), unless the caller passes `streamingBehavior`. Touches `telegram-conversation` (story 15) and `assistant-scheduler` (which may want `followUp` for inline jobs; it can pass it explicitly).
6. **Dropped messages are recorded in memory** (bounded to the last 50 batches, plus a log line and an `onDropped` hook), not persisted. `channel-seam-notify-and-web-push` reports them through the hook. For a CLI-bridge pointer session the server cannot read or clear pi's queues, so nothing is recorded there (abort is still relayed).
7. **New WS frames.** `assistant_open` / `assistant_reset` (client to server) answer `assistant_current { sessionFile, sessionId, cwd }` to the asker, which then opens it through the ordinary `session_load`; `assistant_status` is broadcast to dashboards on every pointer move. With no active assistant both answer a `session_error` ("not active"), a NEW refusal. Alternative: a dedicated HTTP endpoint.
8. **Serial queue + own-creation skip.** All pointer transitions run through one promise chain; sessions the controller creates itself are remembered so their (late) session-created callback is a no-op. Without the skip, `send` replacing a dangling pointer could have its first creation's callback move the pointer BACK.
9. **Web placement.** The Assistant entry is a sidebar nav row (shown only while `active`); Reset is a top-bar button shown only on the current assistant session. Not added to the empty-state home.
10. **Changeset bump is `minor`** (new user-visible web surface and status field).

Observed, not changed (out of scope): after a reset, if another tab is STILL viewing the old assistant session, opening the new one shows the existing folder-conflict banner (read-only until "Continue anyway"), because both sessions live in the assistant folder. That is the same rule a web `/new` already follows in any occupied folder; whether retired assistant sessions should count as occupants is a follow-up question.
