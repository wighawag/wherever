# assistant-schedule-tools-absent-when-not-active: decisions

Dated 2026-10-31 (task implementation).

1. **Reverses an earlier acceptance criterion.** `work/tasks/done/assistant-schedule-tools-server.md` (its decision 4) required that "With the lock held by another server, the tools return a clear lock-state error". That is reversed, as decided in the grilling of 2026-10-31 (Q4): a server whose assistant is not active (lock `refused` or `error`) now registers none of the four schedule tools and adds no timezone line, aligned with `assistant_notify`. The real-server test for the refused case (`server/test/assistant-tools-server.test.ts`) now asserts the opposite, and `server/test/assistant-notify-server.test.ts` no longer expects `assistant_schedule_add` on a refused server.

2. **Mechanism: the pool gets no hooks, the CLI router keeps them.** In `server/src/index.ts` the `AssistantSessionHooks` are still built while `assistantFolder` is CONFIGURED (the CLI twin router reads them, so a terminal pi's twin answers `assistantNotActiveError`), but `sessionPool.setAssistantSessionHooks` is called ONLY while `assistant.status.active`. Considered instead: gating inside `assistantSessionParts` on an `active` flag in the hooks. Rejected because "no hooks" is already the proven "byte-identical to unset" path (`composeServerAgentParts` with `assistant: undefined`), so the refused server reuses it rather than a second code path that must also stay identical. Touches: the CLI twin ops (unchanged), `assistant_notify` registration (unchanged: it was already active-only).

3. **Boot-window message.** The task says the tools answer "still starting" in the short window where the assistant is active but the scheduler has not started. The code answered `assistantNotActiveError(lock)` there, which on an active server reads "configured but NOT active ... (folder lock held)", contradicting itself. Chosen: `access()` answers `the assistant scheduler is still starting; try again in a moment` while active and the backend is not yet set (mirroring the channels' existing "still starting" for `assistant_notify`); the lock-state error is kept for configured-but-not-active. Alternative: leave the old message. The window is effectively unobservable (the scheduler starts before the server listens), so the user-visible impact is nil; it only affects the CLI twin ops and server tools during boot.
