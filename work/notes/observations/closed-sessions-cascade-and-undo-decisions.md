# closed-sessions-cascade-and-undo: in-scope decisions (2026-05-31)

Recorded by the agent that built task `closed-sessions-cascade-and-undo`, for the reviewer and the human to ratify or reverse.

1. **How N is fetched: a small query, `GET /sessions/owned?sessionFile=`, answering `{sessions}`.** Not a listing field: a transitive ownership query per listed session (thousands) would slow every `/sessions`. N is the members a cascade would NEWLY close: the owned subtree, inside the sessions dir, minus sessions already closed (so an orchestration whose children are all closed closes without a question). Alternative considered: return the raw subtree and let the web subtract; rejected because the web only knows the closed flag of listed sessions, the same blind spot as `ownedChildren`. Touches: `index.ts` routes, `web/src/lib/session-store.ts` `closeApi.owned`.
2. **N is fetched on EVERY close**, not only when the sidebar sees listed children: ownership can reach sessions the listing does not show. A failed lookup counts as 0 and the session closes alone, so a close never depends on shipmates. Cost: one local GET per close.
3. **Cascade members are filtered to the sessions dir** (`sessionPool.isSessionFile`), like every close; a shipmates ownership record pointing elsewhere is ignored. The cascade-delete path does not filter; close mirrors the close endpoint's own path rule instead.
4. **The prompt is a modal (`CloseCascadePrompt.svelte`, mounted once in `+page.svelte`)** with three answers: "Close all" (default, focused), "Only this one", Cancel (also Escape). Chosen over an inline row prompt so the top-bar close gets the same question, including on mobile where the sidebar is hidden. A new close while a question is open cancels the old question.
5. **Banner lifetime: one banner, the latest close only.** A newer close replaces it; Undo or the dismiss (x) clears it; otherwise it clears itself after `CLOSE_BANNER_MS` = 30 s (story 19's "short"). It is client-only state (not per device synced, not persisted across reloads). Alternative: one banner per batch kept as long as the delete banner (7 days); rejected since a close is reversible anyway via Show closed + Reopen. No banner when the close took nothing (a re-close).
6. **The banner lives in the sidebar only** (top of `SessionBrowser.svelte`, beside the cascade-delete banner, as the task says). A top-bar close on mobile therefore shows it once the sidebar is opened, within the 30 s.
7. **Request shapes refused with 400:** `cascade: true` on a reopen, `batch` with `closed: true`, `batch` together with `sessionFile`, and a batch id not shaped like `c_<hex>`. An unknown or already undone batch is NOT an error: `{batch, sessions: []}`, so a retried undo is idempotent.
8. **Cascade unstar loop runs over the sessions the close newly took** (`result.sessions`), not the request's files: an already closed member is never starred (starring reopens), so this only avoids touching entries the close did not create.
