# Decisions taken while building `telegram-files` (2026-10-31)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/telegram-files.ts` (module JSDoc, the limits, `attachmentPlan`, `saveUploaded`, the notes), `server/src/telegram-channel.ts` (`TelegramFetch`, `MEDIA_GROUP_DELAY_MS`, `handle`, `converse`, `download`, `callMultipart`), `server/src/telegram-replies.ts` (`sendAttachment`), `server/src/assistant-channels.ts` (`channelMessageText`, `onUserMessage`), `server/src/index.ts` (the `uploadDir` / `maxUploadBytes` wiring). Documented in `CONTEXT.md` "Telegram files, both ways".

1. **"Upload staging" means the upload DIR.** The task says files land in "upload staging (the same place web uploads land)". Web uploads land in `resolveUploadDir(config, cwd)`; `<state>/upload-staging` is only the chunked-upload scratch area, which is GC'd after 24 h and is refused as a download root. Telegram files therefore go to `resolveUploadDir(config, assistantFolder)` (following `uploads.type`), with the web's `<timestamp>_<name>` naming. Alternative: the staging dir, rejected for the GC and download reasons.
2. **The paths are written into the text by the DISPATCHER** (`channelMessageText`, a server twin of the web's `buildAttachmentMessage`, to be kept in step), so any later channel (WhatsApp) gets the same format. The channel downloads and passes `ChannelUserMessage.files`. A text-only message is still sent untouched (no trimming), so `/skill:` and the routing behaviour are unchanged.
3. **Limits are the cloud Bot API's**: 20 MB download (also capped by `uploads.maxBytes`), 10 MB `sendPhoto`, 50 MB `sendDocument`, whatever `apiBaseUrl` points at (a local Bot API server allows more; not detected). Photos only for `.jpg` / `.jpeg` / `.png` / `.webp` (a `.gif` would lose its animation as a photo); a refused `sendPhoto` falls back to `sendDocument`.
4. **Oversize outbound note** names the file, the size, the limit and its server path, and says the web app can download it. Inbound oversize: a note per refused file; the rest of the message (caption, other files) still reaches the assistant. A file whose size Telegram announced over the limit is refused before `getFile`; otherwise the downloaded byte count is checked.
5. **Albums** are gathered for 1.2 s (pi-telegram's `TELEGRAM_MEDIA_GROUP_DEBOUNCE_MS`) after their last message and sent as ONE message, captions joined by a blank line. Any other message (or another album) arriving meanwhile flushes the pending album first, and every inbound message runs through one serial chain, so order holds. Cost: the polling offset is advanced when an album message is gathered, so a crash inside that window loses the album (Telegram will not replay it).
6. **Commands are a TEXT message's**: a caption `stop` / `/new` / `/reset` on a file is text for the assistant, not a command. A `!` caption is still refused, before anything is downloaded.
7. **Unsupported media** (voice notes, which the spec puts out of scope, plus videos, audio, animations, stickers) answer `UNSUPPORTED_MEDIA_REPLY` ("Only text, photos and documents ..."); before this task such messages were silently dropped. Any caption with them still goes through.
8. **No upload dir configured on the channel** (only possible for a direct `TelegramChannel` without the option; index.ts always passes one) answers `FILES_UNAVAILABLE_REPLY`.
9. **Outbound reads `details.path` of a successful `attach_file` `tool_execution_end`** (present for server sessions and CLI-bridge sessions alike), not the `tool_execution_start` args: the result carries the resolved real path and failed calls (`isError`) are skipped. The send joins the reply serial chain, so the file follows the text written before the call. No caption is added.
10. **`TelegramFetch` widened** (method `GET`, an optional `FormData` body, optional `arrayBuffer()`), still satisfied by the global `fetch`; the test fake (`server/test/fake-bot-api.ts`) gained `addFile`, `media`, `getFile`, the file download route, and multipart parsing for `sendPhoto` / `sendDocument` in both its `fetch` and `listen()` modes.
11. **Changeset bump is `minor`** (a new user-visible capability), as for the other Telegram tasks.
