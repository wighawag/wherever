# Decisions taken while building `telegram-conversation` (2026-10-31)

Recorded per the work contract so a reviewer can ratify or reverse them. Code sites: `server/src/telegram-channel.ts` (module JSDoc, `converse`, `markSteer`, `notify`, `reportDropped`, the reply constants, `formatTelegramNotification`, `sessionLink`, `formatDroppedReport`), `server/src/telegram-replies.ts` (module JSDoc, `TELEGRAM_TEXT_LIMIT`), `server/src/assistant-channels.ts` (`ChannelContext`, `ChannelControllerPort`, `onUserMessage`), `server/src/assistant-controller.ts` (`AssistantSendOptions`, `abortCurrent`). Documented in `CONTEXT.md` "The Telegram conversation".

1. **Channel messages are always sent with `streamingBehavior: 'steer'`** (the dispatcher passes it to the controller's `send`). pi uses it only while a turn runs (ADR 0003's steer-on-submit), and it keeps a message that races the start of a turn from being refused by pi ("Agent is already processing") instead of steering. Routing is unaffected (both record into the prompt-or-steer queue). The scheduler's own sends are unchanged. Alternative: keep the controller's `isStreaming ? 'steer' : undefined`, which can throw in that race.
2. **"Steered" is decided by `isStreaming` at dispatch time**, reported through the new `onDispatch` / `onDispatched` hooks (controller `send`'s optional 4th `{onDispatch}`; `ctx.onUserMessage(message, {onDispatched})`). pi's own `preflightResult` disposition (`queued` vs `started`) would be exact, but the pool does not expose it to callers; the window where the two disagree (a turn starting or ending inside pi's input handlers) only affects whether the marker is shown. Alternative: a pool API returning the disposition; reversible later behind the same hook.
3. **The channel context gains `resetSession()` and `abortTurn()`**, backed by the controller's `reset()` and a new `abortCurrent()` (abort the current session's running turn, pointer kept; NOT queued behind the controller's serial queue, so a stop is immediate). `ChannelControllerPort.reset` / `abortCurrent` are optional so a minimal fake still works (the channel then answers an error / "Nothing is running"). Any future channel (WhatsApp) uses the same two.
4. **Steer marker:** the reaction `✍` (one of Telegram's allowed reaction emoji, read as "writing it in"); when `setMessageReaction` fails, the note `↪️ Added to the current reply.` sent as a reply to the user's message (`reply_parameters`, `allow_sending_without_reply`).
5. **Ordering:** an inbound message is handled (and the polling offset advanced) once it is DISPATCHED to the session, not when its turn ends, so the next message is judged against the right state and polling goes on; a started turn never blocks polling (so `stop` works).
6. **Commands:** `stop` matches the whole message case-insensitively (as pi-telegram), plus `/stop` (also `@<bot>`); with nothing running it answers `Nothing is running.`. `/new` and `/reset` reset even with trailing text; a failed reset answers its error. Other commands (`/status`, `/compact`, `/skill:`) are passed to pi untouched; pi-telegram's own `/status` and `/compact` were not ported.
7. **`!` is refused in the channel with an explanation** (`SHELL_REFUSAL_REPLY`), before the dispatcher's own refusal, which stays as defense in depth.
8. **Each assistant MESSAGE with text is delivered at its own `message_end`** (a turn with tool calls in between can send several messages), not only the last one at `agent_end` as pi-telegram does: per-message routing (ADR 0014) can switch the destination mid-run (a steer), and CLI sessions do not forward `message_start`.
9. **`TELEGRAM_TEXT_LIMIT` is 4000**, not 4096: JS lengths are UTF-16 units (never fewer than Telegram counts) and the margin keeps every part safely under the limit the task names. Hard splits never cut a surrogate pair.
10. **Preview cadence:** the first preview of a message goes out at once, later ones at most every 750 ms (pi-telegram's throttle). Unsupported drafts are remembered for the life of the channel.
11. **Ends:** an aborted message ends its draft by sending the partial text the user saw plus `⏹ (stopped)`, silently (superseded: it first sent an EMPTY `sendMessageDraft`, which the Bot API documents as a "Thinking..." placeholder, not a clear; see CONTEXT.md "Ending a draft"; a fallback preview message stays as it was, since `stop` is answered separately); an error message sends `⚠️ The assistant failed: <error>` after any text; a tool-call-only message sends nothing. A failing send to the assistant is answered `⚠️ The assistant could not take your message: ...`.
12. **Notification text:** `🔔 <source>: <title>`, a blank line, the body, a blank line, `<publicUrl>/#<sessionId>` (trailing `/` or `#` of `publicUrl` trimmed; only an http(s) `publicUrl` counts). Sent directly, outside the reply chain, so it is never delayed by or folded into a reply. While unpaired (or stopped) the Telegram delivery is a failure, so `assistant_notify` still succeeds only if another channel delivered.
13. **Dropped report:** one message (split when long), `⚠️ The assistant was reset before it read ...` or `⚠️ The turn was stopped before it read ...`, then one `• <text>` per dropped message, ending "send again if still needed".
14. **Not ported:** pi-telegram's typing indicator (`sendChatAction`); the draft preview already shows activity.
15. **Test harness:** `server/test/fake-bot-api.ts` gained `sendMessageDraft`, `editMessageText`, `setMessageReaction` and `failMethods` (answer a 400, to exercise the fallbacks); `TelegramChannelOptions.replyThrottleMs` exists so unit tests run without the 750 ms throttle.
16. **Changeset bump is `minor`** (a new user-visible conversation channel).
