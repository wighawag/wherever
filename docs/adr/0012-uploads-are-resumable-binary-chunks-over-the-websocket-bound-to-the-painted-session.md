# Uploads are resumable binary chunks over the WebSocket, bound to the painted session

Composer uploads go over the EXISTING WebSocket as raw binary chunks with server-acknowledged offsets (`upload_begin` / chunk frames / `upload_finish`), negotiated by a `connected.capabilities: ['upload.v1']` flag, rather than over HTTP POST or a tus-style HTTP protocol.

WebSocket because mobile browsers silently block non-simple POSTs (and their preflights) against the self-signed / CN-mismatched certificates this server commonly runs with, while the already-trusted socket is immune (`docs/mobile-upload-optimization.md`). Chunked with acked offsets because a single multi-MB frame starves the heartbeat (the pong queues behind it, so the upload kills its own socket), offers no progress, and must restart from zero after a drop. Resume is keyed by a client-generated, validated, unguessable `uploadId`. Partials live in ONE server-owned staging dir under the state dir (`getWhereverStateDir()/upload-staging/`) with a sidecar recording the target dir chosen at begin and, once finished, the saved path. That keeps them out of every download root, makes GC a single scan, survives a session being unloaded mid-upload, and makes completion idempotent across a lost reply or a server restart. `maxPayload` is deliberately NOT shrunk: the same server carries legacy base64 uploads and CLI-bridge frames with base64 images.

The write gate binds an upload to the session the socket PAINTED (`session_created` of its last `session_load` / `session_new`), not only the one it is attached to. With fast-first loading, a cold session is painted seconds before the socket is attached, and after an idle eviction that window is exactly when resumed uploads arrive. Binding to the attached session alone refused them, or (today's legacy behaviour) wrote them into tmp, or into another session's folder under the wrong read-only verdict. Waiting for `session_ready` was rejected because a folder-missing load never sends one. POST cannot see per-viewer state, so it cannot enforce the folder-conflict observe-only lock; that limitation is accepted and documented.
