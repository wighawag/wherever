# Restore jobs are server-owned and keyed by target path

When the dashboard restores a session's missing working folder (cloning the repository, or creating the folder), the operation runs as a job owned by the SERVER and keyed by the resolved absolute TARGET PATH, never by the requesting socket, client, or session. Progress is broadcast to whichever clients currently match that path (by attached session cwd or pending load target), so subscription is DERIVED rather than registered.

The alternative, a job scoped to the requesting connection, is simpler and wrong for the actual usage: the primary client is a phone on a flaky link, and a recursive clone of a real repository takes minutes. Path-keying is what buys the three properties that make the feature usable at all: the clone SURVIVES a dropped socket or a locked screen; a reconnecting or second device re-attaches to the RUNNING job and repaints its progress instead of being offered a fresh start; and a second request for the same folder COALESCES into the existing job instead of racing a competing clone into the same directory. It also gives one honest place to report that a clone of a DIFFERENT URL is already in flight for that path.

The same registry serves both entry points (restoring a loaded session's folder, and creating a new session in a not-yet-cloned folder), which is what keeps a single clone implementation in the codebase after the previous synchronous helper is deleted. The two entry points differ only in their ending: a loaded session asks the user to reload (a live agent is a load-time decision), while a new session has nothing to reload and so continues into creation automatically once the job succeeds.
