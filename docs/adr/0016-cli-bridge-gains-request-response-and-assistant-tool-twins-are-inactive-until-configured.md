# The CLI bridge gains a request/response path, and the `assistant_*` tool twins are registered inactive in CLI sessions until the assistant is configured

**Status:** accepted

Until now the CLI-bridge connection (the `@wherever-dev/pi` extension's WebSocket to the server) only carried fire-and-forget events up (`cli_register`, `cli_event`) and commands down, and every dual-registered tool (`attach_file`, `say`) was deliberately self-contained. The `assistant_*` tools (spec `assistant-session-and-channels`) act on server state (the schedule, the channels), so in a terminal pi session they must CALL the server and wait. We add `cli_request {id, op, args}` / `cli_response {id, ok, result | error}` with correlation ids and a timeout, plus a server push `assistant_info_changed`, and the server resolves the calling session from the bridge registration so origin is stamped server-side, never trusted from the extension.

The CLI twins are ALWAYS registered but INACTIVE (`defaultActive: false`), and the extension activates them with `setActiveTools` only once its cached `assistant_info` says the assistant is configured (at register, and on an `assistant_info_changed` push). The overriding requirement is that a disabled assistant leaves every terminal pi session exactly as it is today: the extension is installed for every terminal pi, including sessions never connected to wherever, so always-active twins would add five tools to all of their prompts. Accepted costs: an unconfigured user never sees the "not configured" error (the tools are simply absent), and in a very fast `pi -p` the first turn can start before `assistant_info` arrives, so the tools are missing on that turn. Once active, a call still fails clearly at call time (bridge disconnected or disabled, server reports not configured, timeout). An old server is detected by TIMEOUT, because the server's WS handler has no default case and `cli_register` has no ack, so an unknown `cli_request` is silently dropped. Server-built sessions, by contrast, register the tools only when `assistantFolder` is configured, since the server knows the answer at build time.

`cli_register` also gains `isNew` (the session context had no messages at `session_start`, sent true only on the first register after it; an entry count is wrong because pi writes model/thinking entries into every new session) and `capabilities`, and the extension forwards `agent_settled`. Older extensions without these degrade explicitly (no pointer move for CLI-created sessions; `agent_end` fallback for settle).
